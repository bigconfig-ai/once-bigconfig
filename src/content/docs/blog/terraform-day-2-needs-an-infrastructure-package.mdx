Terraform is great at Day 1.

Run `terraform apply`, and the machine appears. The bucket exists. The IP address is allocated. The load balancer is online. The provider graph did its job.

But the operational workflow usually does not end there.

The IP has to become a DNS record. The DNS record may have to feed an application config. A cache may need to be purged. Ansible may need to configure the host. SMTP records may need to be published before a provider can verify a domain. A team or an agent may need a report that says what happened and what is safe to do next.

That is Day 2.

The right instinct is not to replace Terraform. The right instinct is to orchestrate Terraform with the other tools that complete the job.

The question is where that orchestration boundary should live.

![Terraform output flows through a BigConfig package into DNS, cache, Ansible, notifications, and agent-safe lifecycle verbs.](/blog/terraform-day-2-needs-an-infrastructure-package.png)

## The shared diagnosis: do not reinvent the wheel

A good Day 2 workflow keeps the tools that already work.

Terraform or OpenTofu should still provision the cloud resources. DNS APIs should still own DNS records. Cache APIs should still purge caches. Ansible should still configure machines. Cloud CLIs and provider SDKs should still do the low-level work they are good at.

The mistake is leaving the glue as a forgotten shell script, a wiki page, or a sequence of commands that only one person remembers.

A better shape is:

```text
provision infrastructure
  -> read outputs
  -> update DNS
  -> render app config
  -> configure the host
  -> purge cache
  -> report what changed
```

That is the right problem.

BigConfig agrees with that diagnosis.

The difference is that BigConfig makes the workflow an **infrastructure package** instead of making a YAML workflow the main product interface.

## YAML workflow or infrastructure package?

A central YAML orchestrator can be useful. It can give teams plugins, schedules, approvals, a web UI, logs, and a run history. For some organizations, that is exactly the right control-plane shape.

BigConfig is optimized for a different center of gravity.

The BigConfig SDK supports TypeScript, Python, and Clojure. This article uses TypeScript examples because the Once implementation shown below is TypeScript, but the package contract is the same across all three SDKs.

| Question | YAML workflow approach | BigConfig package approach |
|---|---|---|
| What is the workflow? | A declarative flow file interpreted by a platform. | A normal TypeScript, Python, or Clojure package/program with lifecycle verbs. |
| Where does it run? | Usually in a hosted or self-hosted orchestrator. | Locally first: laptop, shell, CI, agent session, container, or future control plane. |
| What is public? | Tasks and plugin configuration. | Package verbs: `validate`, `build`, `create`, `describe`, `delete`. |
| What is private? | Some scripts and plugin internals. | Terraform, OpenTofu, Ansible, templates, provider names, generated files, adapters. |
| What does an agent call? | A workflow/task API. | A small executable package interface. |

This is a comparison, not a dismissal.

The YAML workflow model says: put the whole chain in one orchestrator.

The BigConfig package model says: put the whole chain behind one package boundary.

That boundary matters because the consumer should not have to know whether the package uses Terraform, OpenTofu, Cloudflare, Resend, Ansible, a shell script, a provider SDK, or all of them in sequence.

The consumer should ask a domain question:

```bash
./run package validate
./run package build
./run package create
./run package describe
```

The package should translate that intent into tool execution.

## Terraform output is the handoff ABI

The most important idea in this pattern is the handoff between stages.

Terraform already has a good mechanism for this: outputs.

But a package should not leak provider-specific names to downstream consumers. A DNS step should not care whether the compute provider called the address `ipv4_address`, `public_ip`, `ip_address`, or something else. It should consume a normalized package parameter.

In the TypeScript implementation of the [Once package](/once/), each compute provider renders its own `main.tf`, but each provider exposes the same output shape:

```text
output "params" {
  value = {
    ip = provider_specific_resource.provider_specific_ip_field
    sudoer = "root"
    name = "<{ package }>"
    user = "root"
  }
}
```

Hetzner can map `hcloud_server.node1.ipv4_address` to `ip`. DigitalOcean can map `digitalocean_droplet.node1.ipv4_address` to `ip`. OCI can map `oci_core_instance.ampere_vm.public_ip` to `ip`.

The later DNS template does not need to know those provider names. It only needs the normalized package value:

```text
resource "cloudflare_dns_record" "at_record" {
  name    = "@"
  content = "<{ ip }>"
  type    = "A"
}
```

That is the package boundary doing real work.

It turns provider-specific output into a stable internal ABI between modules.

The TypeScript code that reads the output is deliberately boring:

```ts
function tofuOutput(dir: string): Record<string, any> | undefined {
  const res = spawnSync("tofu", ["output", "--json"], {
    cwd: dir,
    encoding: "utf8",
  });

  if (res.error || res.status !== 0) return undefined;

  const value = JSON.parse(res.stdout || "{}")?.params?.value;
  return value && typeof value === "object" ? value : undefined;
}

export function tofuParams(opts: Opts): Opts {
  const params = opts["big-config.workflow/params"] ?? {};
  const dir = path(opts, TOFU);

  return mergeParams(opts, {
    ...fallbackComputeParams(params),
    ...(tofuOutput(dir) ?? {}),
  });
}
```

The point is not that this is difficult code.

The point is that the coupling is in the package, where it belongs, instead of being spread across every DNS workflow, Ansible inventory, application config, agent prompt, and runbook.

## Hide `main.tf` without hiding Terraform

There is another important boundary here.

BigConfig does not need users to edit `main.tf` directly for normal operation.

The package author can keep provider-specific Terraform or OpenTofu templates under package resources, select the right directory based on params, and render concrete artifacts into `.dist/`.

File content can use template variables such as:

```text
name    = "<{ digitalocean-name }>"
region  = "<{ digitalocean-region }>"
content = "<{ ip }>"
```

Directory selection can be parametric too. A package can choose a provider-specific source directory from params, render only the matching implementation, and keep the public interface stable.

The consumer sees:

```bash
export BC_PAR_PROVIDER_COMPUTE="digitalocean"
export BC_PAR_DOMAIN="example.com"

./run package build
```

The package renders the concrete Terraform, DNS config, Ansible inventory, and other files under `.dist/`.

That is not hiding operational truth. `package build` makes the generated files inspectable before mutation.

It is hiding implementation churn from the public interface.

## The workflow is TypeScript, not accidental YAML programming

Here is the six-stage create pipeline in the TypeScript Once package:

```ts
const TOFU_APPLY = "render tofu:init tofu:apply:-auto-approve";
const ANSIBLE_RUN = "render ansible-playbook:main.yml";

export const create = createWorkflowStar({
  firstStep: PIPELINE_START,
  lastStep: PIPELINE_END,
  pipeline: [
    tools.TOFU, [TOFU_APPLY, optsFn],
    tools.TOFU_SMTP, [TOFU_APPLY, optsFn],
    tools.TOFU_DNS, [TOFU_APPLY, optsFn],
    tools.TOFU_SMTP_POST, [TOFU_APPLY, optsFn],
    tools.ANSIBLE_LOCAL, [ANSIBLE_RUN, optsFn],
    tools.ANSIBLE, [ANSIBLE_RUN, optsFn],
  ],
});
```

Read that as an operational sentence:

```text
tofu
  -> tofu-smtp
  -> tofu-dns
  -> tofu-smtp-post
  -> ansible-local
  -> ansible
```

The first stage provisions compute. The SMTP stage creates the mail-domain resources. The DNS stage publishes records. The SMTP post stage finalizes verification after DNS exists. The local Ansible stage updates the local SSH configuration. The remote Ansible stage configures the host and deploys the applications.

Each stage can render its own files. Each stage can call its own tool. Each stage can receive params from profiles, `BC_PAR_*` overrides, and earlier Terraform outputs.

The public interface is still small:

```bash
./run package validate
./run package build
./run package create
./run package describe
./run package delete
```

That is the difference between "a script that runs Terraform and then some stuff" and an infrastructure package.

The package has a contract.

## Code-first

BigConfig is code-first because operational glue becomes normal package code.

That matters whether your platform team prefers TypeScript, Python, or Clojure.

You can use functions, modules, types, dependency management, test runners, pure report builders, fixtures, and injected runners. You can test validation logic without provisioning a server. You can test report formatting without calling a cloud API. You can keep shell execution behind a runner seam instead of spawning real tools in every unit test.

YAML can describe a workflow, but once the workflow needs non-trivial normalization, validation, fallback behavior, provider-specific branching, reports, and tests, it starts growing a programming language in the wrong place.

BigConfig starts with the programming language and uses templates only where templates are the right tool: generating durable files for Terraform, OpenTofu, Ansible, apps, and CLIs.

## Local-first

BigConfig is local-first because the package can run where the operator already is.

A developer can run it from a laptop. A CI job can run it in a pipeline. An agent can run it inside a coding session. A future control plane can run the same package interface later.

The package does not require the hosted orchestrator to be the source of truth.

This is especially useful for infrastructure development. `package build` can render `.dist/` locally before any mutation happens. A human or agent can inspect the generated Terraform, DNS configuration, inventories, scripts, and reports. The native tools still own their own state, for example Terraform/OpenTofu remote state.

Local-first does not mean anti-control-plane.

It means the package interface exists before the control plane.

## Agent-first

BigConfig is agent-first because agents need small, stable, executable boundaries.

An agent should not need to infer your provider naming conventions, remember which Terraform outputs feed DNS, decide whether a cache purge is safe, know which generated file can be edited, and discover which command mutates production.

Give the agent package verbs.

Let it run:

```bash
./run package validate
./run package build
./run package describe
```

Let it read generated artifacts and summarize reports.

Keep state-changing verbs explicit:

```bash
./run package create
./run package delete
```

That command surface is easier to review than a prompt that says, "Use Terraform, then update DNS, then purge the cache, and be careful."

The agent does not become the platform engineer.

The package captures the platform engineer's workflow in executable form.

## Keep Terraform. Package Day 2.

Terraform is still great at Day 1.

The hard part is the rest of the operational sentence.

Provision the resource. Normalize the output. Feed DNS. Render config. Configure the host. Verify the result. Report what changed. Give humans and agents a small interface they can trust.

That is Day 2 infrastructure work.

BigConfig's answer is not to throw away the tools. It is to put them behind a code-first, local-first, and agent-first package boundary.

Keep Terraform inside.

Expose the package outside.

If that is the shape you want for infrastructure automation, start with [BigConfig](/).
