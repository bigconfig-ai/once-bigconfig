There are two different jobs hiding behind one familiar workflow.

One job is **using infrastructure**: changing the intent for one application, one environment, one team, or one deployment instance.

The other job is **developing infrastructure**: changing the reusable package that knows how to provision, validate, render, and operate that class of infrastructure.

In many Terraform workflows, those jobs look exactly the same:

```bash
git clone git@github.com:company/platform-terraform.git my-app-infra
cd my-app-infra
# edit .tf / .tfvars / module inputs
terraform init
terraform validate
terraform plan
terraform apply
```

That workflow is familiar. It is also overloaded.

The person using the infrastructure and the person developing the infrastructure product are both dropped into the same repository, the same files, and the same tool interface. Sometimes the user only changes a `.tfvars` file. Sometimes they touch a module input. Sometimes they edit real implementation code because that is the only surface available.

That is not self-service. That is accidental authorship.

BigConfig separates the two jobs.

A delivery team operates a **package instance repository** through package lifecycle verbs. A platform team develops the **package source repository** through render and tool loops.

The difference is small in commands and large in architecture.

## The mental model

Use this model when deciding where a change belongs:

| Role | Repository | Edit | Run |
|---|---|---|---|
| Package consumer | Package instance repo | Instance-level intent: `run`, params, app list, environment overrides | `package validate create` |
| Package author | Package source repo | Workflows, templates, validation, reports, resources | `npx . tofu render tofu:init -- tofu plan` or language equivalent |

A package instance repository is the app-owned or team-owned consumer repo for one deployment instance. It contains the copied `run` file, a native manifest generated by `bc-pkg`, pinned package metadata, and local configuration for that instance.

A package source repository is the reusable implementation. It contains package code, templates, validation logic, report builders, resources, and the lower-level tool orchestration.

Terraform or OpenTofu can still be inside the source package. The point is that it stops being the first interface every consumer has to operate.

## Consumer flow 1: clone an existing package instance

If a team already has an instance repository, the consumer workflow should stay boring.

```bash
git clone git@github.com:company/my-app-infra.git
cd my-app-infra
```

Then edit only instance-level intent.

That might be the copied `run` file. It might be a profile map. It might be an application list. It might be environment variables using the `BC_PAR_*` convention.

For example:

```bash
export BC_PAR_DOMAIN="app.example.com"
export BC_PAR_PROVIDER_BACKEND="r2"
```

When ready, run the package lifecycle:

```bash
npx bc-pkg package validate create
```

The important part is the shape of the command.

The consumer is not running raw Terraform. The consumer is asking the package to first validate this instance, then create or reconcile it. The package decides what validation means. It can check required tools, placeholder values, credentials, image references, and other pre-flight conditions before a state-changing step runs.

`create` does not have to secretly validate. The chain makes the ordering explicit: validate first, create only if validation passes.

If the consumer wants to inspect generated output without changing real resources, the package can expose a build step:

```bash
npx bc-pkg package build
```

Rendered files belong in `.dist/`. Treat that directory as generated output, not source.

## Consumer flow 2: bootstrap a new package instance

A new team may not have an instance repo yet. Start from an empty directory and let `bc-pkg` initialize the consumer project.

```bash
mkdir my-app-infra
cd my-app-infra
npx bc-pkg company/app-platform@main package validate
```

On the first run, `bc-pkg` resolves the GitHub ref, pins the package revision, copies the package's root `run` file, writes a native manifest, and forwards the remaining command to the package.

After that first run, the directory remembers the pinned package. You can omit the target spec:

```bash
# edit the copied run file / params for this instance
npx bc-pkg package validate create
```

If you prefer the Python launcher, the same consumer idea looks like this:

```bash
uvx bc-pkg company/app-platform@main package validate
uvx bc-pkg package validate create
```

The exact generated files depend on the launcher and target language. The boundary does not change: the consumer directory is the package instance, and the pinned package is the reusable source.

Commit the instance files you want the team to share. Keep credentials out of source. Use placeholders in copied files and private environment overrides for secrets.

## What a consumer should not edit

A consumer should not have to edit reusable package internals to deploy one app.

If a delivery team needs to change application hosts, domains, image tags, profiles, or safe parameters, that belongs in the instance surface.

If they need to change how the package renders Terraform, how DNS records are generated, how validation works, or which stages compose the workflow, they have crossed into package development.

That may be a valid change. It should happen in the package source repository, not as a one-off mutation in the instance repo.

This is the practical difference between a package and a shared folder of Terraform.

A package gives consumers a supported surface.

A folder gives them implementation files.

## Author flow: develop the package source

Now switch roles.

A platform engineer who owns the reusable package clones the source repository:

```bash
git clone git@github.com:company/app-platform.git
cd app-platform
```

This is where package development happens.

The author edits package code, templates, resource packaging, validation checks, report builders, workflow composition, and tool-specific stages. Terraform/OpenTofu, Ansible, Helm, cloud APIs, and other tools can all live here as implementation details.

After changing the package, the author runs the render/tool loop. In a TypeScript/npm package source checkout, that can look like this:

```bash
npx . tofu render tofu:init -- tofu plan
```

Here `npx .` runs the local package entrypoint from the source checkout. The rest of the command is the package's tool workflow.

Read that command as a development workflow:

1. `tofu` selects the package's OpenTofu tool runner.
2. `render` renders the package templates into `.dist/`.
3. `tofu:init` expands to `tofu init` for the rendered module.
4. `-- tofu plan` passes the raw OpenTofu plan command to the exec step.

Use the equivalent local entrypoint for the package language:

```bash
# Python package source checkout
uvx . tofu render tofu:init -- tofu plan

# Clojure package source checkout
bb run tofu render tofu:init -- tofu plan
```

The package author still gets the power of OpenTofu. The difference is that OpenTofu is no longer the consumer interface. It is part of the package author's inner loop.

Authors should also test the package as a consumer would use it. Local path mode exists for that:

```bash
mkdir /tmp/app-platform-consumer
cd /tmp/app-platform-consumer
npx bc-pkg /path/to/app-platform package build
npx bc-pkg package validate
```

Run local path tests from a separate consumer directory. The point is to verify the package boundary, not to overwrite the package source tree with generated consumer files.

Before publishing a package ref, test the pinned GitHub flow too:

```bash
mkdir /tmp/app-platform-pinned
cd /tmp/app-platform-pinned
npx bc-pkg company/app-platform@main package validate
```

If both the local path flow and the pinned flow work, the package is much closer to being a real product interface.

## Why raw Terraform collapses the roles

Terraform modules are useful. Terraform state is useful. `terraform plan` is useful.

The problem is not Terraform.

The problem is using the Terraform source tree as the public interface for everyone.

When consumers and authors share the same workflow, you get predictable failure modes:

- every consumer has to understand provider configuration and state conventions
- safe app-level changes sit next to reusable implementation files
- agents see a directory full of powerful low-level commands with weak intent boundaries
- platform teams have to document which files are safe instead of exposing a smaller interface
- normal usage changes can accidentally become package source changes

The usual answer is more README text, more wrapper scripts, more CI policy, or a dashboard around Terraform.

Those can help. They do not change the basic shape.

A BigConfig package changes the shape by giving consumers a lifecycle contract and giving authors a separate source development loop.

## A simple rule for teams

Use this rule:

> If the change is about **this instance**, edit the package instance repo. If the change is about **how every instance works**, edit the package source repo.

Examples of instance changes:

- domain name
- application image
- environment-specific params
- provider choice when the package supports multiple providers
- safe runtime overrides through `BC_PAR_*`

Examples of source changes:

- add a validation check
- change a Terraform/OpenTofu template
- add a lifecycle verb
- change the render pipeline
- package new resources
- modify how reports are built

This rule gives delivery teams a smaller surface and gives platform teams a cleaner review boundary.

It also gives agents a better working directory. An agent operating an instance can run `package validate`, inspect `.dist/`, summarize changes, and ask before state-changing verbs. It does not need to infer your whole platform architecture from raw Terraform files.

## The interface is the lifecycle

BigConfig's package lifecycle is intentionally small:

```bash
package validate
package build
package create
package describe
package delete
```

Packages can support chained workflows such as:

```bash
package validate create
```

That is the user interface.

The package source can be as rich as it needs to be. It can render Terraform. It can run Ansible. It can call cloud APIs. It can produce durable artifacts. It can expose more domain verbs when the package needs them.

But the consumer should not start by learning the source tree.

The consumer should operate the package.

The author should develop the package.

Keeping those workflows separate is what turns infrastructure from a shared implementation repo into a package people and agents can safely use.
