BigConfig packages now have starter skills in TypeScript, Python, and Clojure.

That means you can ask Claude Code to scaffold the smallest real BigConfig package in the language you already use, then grow it from there.

The skills are public here:

[github.com/bigconfig-ai/skills](https://github.com/bigconfig-ai/skills)

This is a tutorial for trying them.

The short version is:

1. install the skills into Claude Code,
2. ask for a TypeScript, Python, or Clojure BigConfig package,
3. run the generated package's tests,
4. run `package validate`,
5. run `package build`, and
6. inspect the rendered `.dist/` output.

The important part is not that the generated package says `Hello, world!`.

The important part is that it has the right package shape: a language-native manifest, a root `run` file, packaged resources, lifecycle verbs, tests, and the boundary needed to run through `bc-pkg` later.

## What the skills create

There are three skills:

| Skill | Generated package language | Local verification |
|---|---|---|
| `create-ts-bigconfig-package` | TypeScript | `npm test`, `node run package validate`, `node run package build` |
| `create-py-bigconfig-package` | Python | `uv run pytest -q`, `uv run python run package validate`, `uv run python run package build` |
| `create-clj-bigconfig-package` | Clojure | `clojure -M:test`, `bb run package validate`, `bb run package build` |

Each one creates a minimal package that depends only on the `big-config` SDK.

The starter includes:

- one language-native manifest: `package.json`, `pyproject.toml`, or `deps.edn`
- a launcher-friendly root `run` file
- a single `hello` render stage
- `package validate`
- `package build`
- packaged template resources
- tests
- `BC_PAR_*` environment variable overrides
- a `.dist/` artifact boundary
- the repository shape expected by the [BigConfig Package Spec](/package-spec/)

It is intentionally small.

It is not a production infrastructure package. It does not include real credentials, provider accounts, OpenTofu state backends, Ansible roles, or a cloud deployment pipeline.

It is the seed you want before adding those things.

## Install the skills

Clone the skills repository and symlink the skills into Claude Code's discovered skills directory:

```bash
git clone https://github.com/bigconfig-ai/skills.git
mkdir -p ~/.claude/skills

ln -s "$PWD/skills/create-ts-bigconfig-package" ~/.claude/skills/create-ts-bigconfig-package
ln -s "$PWD/skills/create-py-bigconfig-package" ~/.claude/skills/create-py-bigconfig-package
ln -s "$PWD/skills/create-clj-bigconfig-package" ~/.claude/skills/create-clj-bigconfig-package
```

If you already cloned the repo somewhere else, set `SKILLS_DIR` explicitly:

```bash
SKILLS_DIR=/path/to/skills
mkdir -p ~/.claude/skills

ln -s "$SKILLS_DIR/create-ts-bigconfig-package" ~/.claude/skills/create-ts-bigconfig-package
ln -s "$SKILLS_DIR/create-py-bigconfig-package" ~/.claude/skills/create-py-bigconfig-package
ln -s "$SKILLS_DIR/create-clj-bigconfig-package" ~/.claude/skills/create-clj-bigconfig-package
```

You can also install them per project by symlinking into that project's `.claude/skills/` directory instead of `~/.claude/skills/`.

After that, restart or reload Claude Code if needed so it discovers the skills.

## Scaffold a package

Use the skill that matches the language you want.

For TypeScript:

```text
/create-ts-bigconfig-package
Create a BigConfig package named widget owned by acme.
Use the default description and generate it in ./widget/typescript.
Use the published big-config SDK pin.
```

For Python:

```text
/create-py-bigconfig-package
Create a BigConfig package named widget owned by acme.
Use the default description and generate it in ./widget/python.
Use the published big-config SDK pin.
```

For Clojure:

```text
/create-clj-bigconfig-package
Create a BigConfig package named widget owned by acme.
Use the default description and generate it in ./widget/clojure.
Use the published big-config SDK pin.
```

The skills ask for the package name, GitHub owner, description, target directory, and SDK source. The default SDK source is a pinned GitHub revision of the `big-config` SDK. If you are developing the SDK locally, the skills also document the local-path alternatives.

The package name can be hyphenated. The skills handle the annoying language-specific details:

- TypeScript needs a valid JavaScript identifier for exported functions.
- Python needs a snake_case importable module name.
- Clojure namespaces use hyphens, but source paths munge hyphens to underscores while resource paths keep hyphens.

Those details are exactly why this belongs in a skill instead of in a loose checklist.

## Verify the generated package

After scaffolding, go into the generated package directory and run the language-specific checks.

For TypeScript:

```bash
npm install
npm run build
npm run typecheck
npm test
node run package validate
node run package build
BC_PAR_NAME=REPLACE_ME node run package validate
```

For Python:

```bash
uv sync
uv run pytest -q
uv run python run package validate
uv run python run package build
BC_PAR_NAME=REPLACE_ME uv run python run package validate
```

For Clojure:

```bash
clojure -M:test
bb run package validate
bb run package build
BC_PAR_NAME=REPLACE_ME bb run package validate
```

The normal `validate` command should exit successfully.

The `BC_PAR_NAME=REPLACE_ME` command should fail validation. That failure is intentional. It proves that environment overrides reach the validation report.

The `build` command should render a greeting into `.dist/`. The starter package renders one template through one `hello` stage, so you should see a generated `greeting.txt` containing:

```text
Hello, world!
```

That output is simple, but the behavior is the point. A BigConfig package should be able to render durable artifacts before anything touches real infrastructure.

## Why a skill, not just a template?

A static template can copy files.

A skill can carry the authoring procedure.

The difference matters because creating a package is not only file generation. The agent needs to:

- choose the right language-specific layout,
- derive the package namespace,
- place resources where the renderer can find them,
- preserve kebab-case boundary parameters,
- pin or locally override the SDK dependency,
- run the right verification commands,
- check that `validate` succeeds,
- check that the override failure actually fails, and
- confirm that `build` renders `.dist/` output.

That is procedural knowledge.

A Claude Code skill packages that knowledge for the agent. A BigConfig package packages the resulting operational procedure for everyone else: humans, agents, shells, CI, and eventually `bc-pkg` consumers.

That is the relationship I described in [Skills vs. BigConfig Packages](/blog/skills-vs-bigconfig-packages/):

> Skills make agents smarter. BigConfig makes procedures runnable.

These three skills sit exactly at that boundary. The skill teaches the agent how to create the package. The package gives the world an executable interface.

## Built and verified with agents

These skills were also created using the same agentic development loop they enable.

The loop was not just "write a template and hope."

It was:

1. generate a throwaway package,
2. run the language-native install and tests,
3. run `package validate`,
4. run `package build`,
5. force a `BC_PAR_*` validation failure,
6. inspect the rendered artifact,
7. fix the template, and
8. repeat until the generated package passed.

That matters because package scaffolding is full of small traps: missing resources in installable artifacts, wrong namespace paths, broken module names, forgotten executable bits, or a `run` file that works from the source tree but not from the launcher boundary.

The skill encodes the corrected path.

## From starter package to `bc-pkg`

The generated package can be run directly from its source tree while you are authoring it.

Once you push it to GitHub, it can become a `bc-pkg` target.

For TypeScript or Clojure targets, the npm launcher can initialize and run it:

```bash
npx bc-pkg owner/repo@ref package validate
npx bc-pkg owner/repo@ref package build
```

For Python or Clojure targets, the Python launcher can initialize and run it:

```bash
uvx bc-pkg owner/repo@ref package validate
uvx bc-pkg owner/repo@ref package build
```

The launcher resolves the ref, pins the package, writes the native consumer manifest, copies or links the root `run` file, and forwards the remaining command to the package.

That is why the root `run` file and the package spec matter. They are the handoff between package authoring and package consumption.

You can read the contract here:

[BigConfig Package Spec](/package-spec/)
