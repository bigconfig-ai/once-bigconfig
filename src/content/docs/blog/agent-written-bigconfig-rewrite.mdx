After reading that Bun was rewritten from Zig to Rust, I decided to try the same kind of experiment on BigConfig.

Then I deleted the hand-written version and redeployed this website with the agent-written one.

That was the real test.

BigConfig started as a hand-written Clojure stack. Not just one library, but the stack around it: Selmer for templates, BigConfig as the workflow and rendering engine, Once as the infrastructure package, and the package/runtime layer that makes those procedures runnable from the shell.

The experiment was simple to describe and harder to execute:

> Can an agent rewrite the broader BigConfig stack across TypeScript, Python, and Clojure without losing the operational contract?

First I ported it to TypeScript.

It worked.

Then I ported it to Python.

It worked again.

Then came the surprising part: I used the TypeScript version as the source to regenerate the Clojure version too.

Clojure was both the origin and the final check.

## This was not just syntax translation

The interesting part was not converting one function name into another function name.

The interesting part was discovering which parts of the system were accidentally language-specific.

A hand-written implementation can carry assumptions that are invisible for a long time. Maybe a key shape is natural in Clojure but awkward in Python. Maybe a workflow primitive is easy in TypeScript but not generic enough for Clojure. Maybe a renderer detail works in one runtime because of local conventions, not because the contract is actually clear.

Porting across three languages exposed those assumptions.

Some things had to break.

That was good.

The rewrite forced BigConfig to become more explicit about the contracts that matter:

- the same workflow shape
- the same lifecycle verbs
- the same parameter flow
- the same rendered artifacts
- the same package behavior
- the same boundary between the engine and tool runners
- the same string keys at runtime boundaries

Those constraints made the system more generic.

They also made it cleaner.

## Why the contract matters

BigConfig is not trying to be another prompt format.

The point of BigConfig is that procedural knowledge should be software.

A BigConfig package describes how to do something operational: provision a server, configure DNS, render files, run OpenTofu, run Ansible, validate the result, describe the system, and safely delete it later.

That procedure should not only live in a runbook.

It should not only live in a chat transcript.

It should be executable.

That is why the package contract matters. A package exposes verbs such as:

```bash
validate
build
create
describe
delete
```

Those verbs are not just CLI conveniences. They are authority boundaries.

An agent can run `validate` or `describe` with read-only credentials. A CI job can run `build` to render durable artifacts. A human can keep `create` and `delete` behind approval.

The same procedure can be called by an agent, a human in a terminal, a CI pipeline, a cron job, or another script.

That is the difference between agent-native procedural knowledge and shell-native procedural knowledge.

Skills make agents smarter.

BigConfig makes procedures runnable.

## The broader stack had to move together

This is why the rewrite had to involve more than the BigConfig engine.

The engine is only one layer.

Selmer provides the template language. BigConfig provides workflows, rendering, step dispatch, parameter threading, and runner seams. Once uses that engine to package a real infrastructure workflow. The launcher layer makes packages invokable from Python and TypeScript tooling while still being able to launch Clojure, Python, or TypeScript target packages.

If only one layer works, the story is not convincing.

The useful proof is that the whole path works:

```bash
npx bc-pkg bigconfig-ai/once@typescript package validate
npx bc-pkg bigconfig-ai/once@typescript package build
npx bc-pkg bigconfig-ai/once@typescript package create
```

Or the same package shape through Python or Clojure targets.

The language is secondary.

The contract is primary.

## Then I used it in production

The public BigConfig website, `bigconfig.ai`, is deployed with `once`.

`once` is a BigConfig package. It drives a deployment through infrastructure and configuration stages, renders the files it needs, and exposes the lifecycle verbs that make the operation repeatable.

It is also designed with disaster recovery in mind. The deployment path is not just a one-off shell session on my laptop. It is packaged operational knowledge.

So I did the thing that makes a rewrite real.

I deleted the manually written BigConfig version.

Then I deployed the agent-written version.

No incident.

That is the part I care about.

Not because “an agent wrote code” is magic.

It is not.

The important part is that the code was inside a system with explicit contracts, reusable libraries, tests, rendered artifacts, and a production workflow that could prove whether the abstraction still held.

Agents are much more useful when they are not just producing text.

They are useful when they can work inside a software-shaped boundary.

## The lesson

I do not think the interesting future is agents writing random glue code forever.

The interesting future is agents helping maintain executable operational systems.

That requires structure:

- lifecycle verbs
- package boundaries
- library reuse
- generated artifacts
- tests and parity checks
- credentials scoped to the action
- humans still deciding when destructive operations run

Without that structure, agentic DevOps becomes a probabilistic shell with production credentials.

With that structure, an agent can help evolve the procedure itself.

That is why the rewrite matters to me.

BigConfig is the Open Agent Packages Ecosystem because the package is the stable unit of operational knowledge.

A package is like a skill, but executable.

It can be inspected by an agent, run by a human, validated by CI, scheduled by cron, and reviewed as software.

The thesis is simple:

Procedural knowledge should not only live in prompts or runbooks.

It should be executable, composable, testable, versioned, and runnable from the shell.
