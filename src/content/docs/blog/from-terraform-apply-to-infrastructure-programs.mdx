DevOps innovation feels stuck.

Every week there is another wrapper around Terraform. Another dashboard for plans. Another GitOps controller. Another YAML dialect. Another attempt to make `apply` safer by surrounding it with approvals, comments, queues, policies, drift checks, and a web UI.

Some of those tools are useful.

But another Terraform wrapper is not a new operating model.

The problem is not Terraform. The problem is that we keep making low-level tool interfaces the public interface for operations.

We hand delivery teams `terraform apply`, `helm upgrade`, YAML, provider schemas, cluster-specific CRDs, and a long page of platform conventions. Then we call it self-service.

It is not self-service. It is tool delegation.

A platform team should be allowed to love Terraform and Helm. They are powerful tools. They encode hard-won operational knowledge. They solve real problems.

But the delivery team should not need to learn your whole toolbox to deploy an application. And an agent should not need to become a mediocre Terraform operator, Helm operator, Kubernetes operator, cloud console operator, and CI operator all at the same time.

The platform tool should be an implementation detail, not the product interface.

## GitOps was built for an older cost model

The GitOps era made sense.

When custom operational software was expensive to write and expensive to maintain, configuration files were the lowest common denominator. Put YAML in Git. Let a CLI or controller reconcile it. Make the code someone else's problem.

That was a rational trade.

If writing a real program for every operational workflow is too expensive, you compress the workflow into configuration. You adapt your requirements to the tool. You teach everyone the tool's nouns and verbs. You turn every platform capability into a file format.

That is how we ended up with a world where the user interface to production is often:

```bash
terraform plan
terraform apply
terraform destroy
```

Or:

```bash
helm upgrade --install ...
kubectl apply -f ...
```

Those are not product interfaces. They are tool interfaces.

They expose the implementation. They leak the platform team's mental model. They force every delivery team, every CI job, and every agent to reason at the wrong layer.

The agent era changes the cost curve.

Not because code is magically safe. Not because agents should write unreviewed infrastructure from scratch. That is how you get a very fast incident.

The change is smaller and more important: writing and maintaining glue code, adapters, tests, report builders, and package surfaces is now cheap enough that we can stop pretending raw tool commands are the only affordable interface.

We can afford operational programs.

## The package is now a program

A package should not be a folder of Terraform with a README.

A package should be a program.

It should have a public command surface. It should decide what verbs make sense for the domain. It should render durable artifacts. It should validate inputs. It should describe reality. It should know which operations are safe for an agent and which operations require human authority.

This is the important shift:

> Once the package is a program, `plan`, `apply`, and `destroy` are no longer the only verbs available.

A BigConfig package already has a small lifecycle vocabulary:

```bash
package validate
package build
package create
package describe
package delete
```

That vocabulary is intentionally small in the [BigConfig Package Spec](/package-spec/). It gives package authors a common external contract: one root manifest, one root `run` file, installable code and resources, and lifecycle commands that `bc-pkg` can forward to.

But the spec is not a cage.

A real infrastructure package can expose the verbs the domain needs:

```bash
package cost-analysis
package backup
package restore
package rollback
package upgrade
package rotate-keys
package audit
package migrate
```

Those verbs are not decoration. They are the product interface.

A database package should have backup and restore. A SaaS deployment package should have upgrade and rollback. A security package should have audit and rotate-keys. A cost-sensitive package should have cost-analysis.

Forcing all of that through `apply` is not simplicity. It is a lack of vocabulary.

## Kubernetes operators proved the idea, then siloed it

Kubernetes operators are one of the clearest signs that the industry already knows configuration is not enough.

An operator is operational knowledge expressed as a program. It watches state. It reconciles. It encodes lifecycle behavior. It turns domain knowledge into software.

That is the good part.

The problem is where the knowledge lives.

Kubernetes operators run inside Kubernetes. Their operational knowledge is naturally siloed inside the cluster. That is fine when the whole problem lives in the cluster. It is awkward when the caller is an agent on a laptop, a sandboxed coding agent, a CI job, a local shell, or a separate control plane.

My agent runs on my computer. My CI runs somewhere else. My control plane may not be Kubernetes. My infrastructure may include DNS, SMTP, object storage, cloud networking, a VM, an application, and a Kubernetes cluster.

If the operational knowledge is trapped behind a Kubernetes runtime boundary, integration becomes the user's problem again.

That is the wrong direction.

The package should be the operational boundary.

It can call Kubernetes. It can install Helm charts. It can apply CRDs. It can talk to cloud APIs. It can run Terraform or OpenTofu. It can run Ansible. It can call an operator-facing API if that is the right implementation.

But the public interface should be a package program that the agent, the shell, CI, and the control plane can all run.

## Platform teams keep the tools

This is not an argument for throwing away Terraform.

It is the opposite.

Platform teams should keep Terraform, Helm, OpenTofu, Ansible, Kubernetes operators, cloud SDKs, provider APIs, policy engines, and all the other tools they need.

They should stop shipping those tools as the user experience.

A delivery team does not want a low-level infrastructure curriculum. It wants to know:

- can I deploy this?
- is the environment valid?
- what will change?
- what does it cost?
- is it healthy?
- can I roll back?
- can I back it up?
- can I upgrade safely?

Those are domain questions, not Terraform questions.

The package is where the platform team translates from domain intent to tool execution.

Inside the package, use whatever is right. Render Terraform. Generate Ansible inventories. Install Helm charts. Call APIs. Write lock files. Produce reports. Store output under `.dist/`. Compose six stages if the domain requires six stages.

Outside the package, expose verbs.

That is the separation of concerns DevOps keeps promising and rarely delivering.

## Agents need an executable contract

Agents make this problem impossible to ignore.

A human can slowly learn your platform's tribal knowledge. A delivery engineer can memorize which Terraform workspace corresponds to which environment, which Helm values are safe, which `kubectl` command is read-only, which CI workflow is allowed to mutate production, and which Slack channel to ask when the script fails halfway through.

That is already bad.

An agent makes it absurd.

Do we really want every agent to learn every low-level tool and every local convention? Do we want it to infer the difference between a safe read-only command and a destructive one from a wiki page? Do we want it to discover rollback by reading a runbook written in 2021?

No.

Give the agent an executable contract.

Let it run:

```bash
package describe
package validate
package build
```

with read-only or no credentials.

Let it inspect `.dist/`. Let it summarize what changed. Let it recommend the next action.

Keep state-changing verbs behind explicit authority:

```bash
package create
package delete
package rollback
package upgrade
```

The package contract becomes a boundary between advice and action.

That boundary is much easier to review, test, automate, and secure than a pile of prompts wrapped around a production shell.

## What BigConfig makes concrete

BigConfig is my attempt to make this shape boring.

A BigConfig package is a normal language package with a small executable contract. `bc-pkg` can pin it from GitHub to a commit SHA, initialize a consumer directory, copy or link the root `run` file, write a native manifest, and forward commands to the package.

The package can be TypeScript, Python, or Clojure. The launcher implementations are Python and npm, and both can run Clojure target packages. The language is not the point.

The point is that the package is runnable by the outside world.

From a shell:

```bash
npx bc-pkg bigconfig-ai/once@typescript package validate
```

From Python tooling:

```bash
uvx bc-pkg bigconfig-ai/once@python package validate
```

From a local development checkout:

```bash
npx bc-pkg ../once/typescript package build
```

The package can use profile params, `BC_PAR_*` environment overrides, templates, workflow steps, plugins, and generated artifacts. It can render real files before it mutates real infrastructure. It can separate `validate` from `create`. It can make `describe` read-only. It can make destructive operations explicit.

That is not a Terraform wrapper.

That is an infrastructure program.

## Stop exposing the assembly language

The future of DevOps is not every delivery team becoming a part-time platform engineer.

It is not every agent learning to operate raw Terraform, Helm, Kubernetes, cloud CLIs, and internal scripts.

It is not another UI around `apply`.

The future is platform teams packaging operational knowledge as software and exposing the verbs the domain actually needs.

Platform teams can keep their tools.

Delivery teams should get a package.

Agents should get an executable contract.

CI should get commands that mean something.

Control planes should call programs, not scrape runbooks.

That is the move from Terraform apply to infrastructure programs.
