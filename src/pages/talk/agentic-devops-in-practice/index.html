An operating model, not just a powerful agent

Don't Give Agents Full Power

Agents with the same credentials as the operator are not assistants — they are unbounded operators with a prompt interface.

The agent advises. The operator acts.

The safe pattern is boring enough to repeat.

The Operating Model

  1. Launch a disposable Docker sandbox with @bigconfig/bb
  2. Give the sandbox read-only credentials only
  3. Agent runs describe + validate to inspect
  4. Agent recommends the next step
  5. Operator decides and runs create / delete

npx @bigconfig/bb shell → container sandbox → pi.dev agent

The Four Verbs

VerbCredentialsDefault actorPurpose
describe Read-only Agent in sandbox Inspect current state
validate Read-only Agent in sandbox Check reality vs expectations
create Full Operator Provision or change resources
delete Full Operator Destroy resources

The agent explores. The operator executes.

Enforcing the Boundary

Read-only credentials

One rule removes a class of failures. create and delete cannot succeed from inside the sandbox.

ForceCommand CLI

Narrow, auditable SSH commands as policy enforcement points — not a broad MCP server.

agent in sandbox → narrow CLI over SSH → ForceCommand enforces → result

Patterns vs Anti-patterns

✅ Follow

  • Disposable Docker sandbox
  • Read-only credentials only
  • describe / validate for agents
  • Operator runs create / delete
  • Narrow ForceCommand CLIs

❌ Avoid

  • Agent on operator's host
  • Full credentials to agent
  • No read-only vs state-changing separation
  • Agent runs create / delete autonomously
  • Broad MCP for infra operations

The Golden Path

"Use describe and validate to inspect the current state. Explain what you found and suggest the next step. Do not run create or delete."

A better prompt is not "Fix production."
It is a structured investigation.
