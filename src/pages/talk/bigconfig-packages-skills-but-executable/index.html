Thesis

Skills make agents smarter.
Packages make operations runnable.

A BigConfig package is procedural knowledge expressed as software: versioned, testable, executable, and safe to expose through a small command surface.
State the central distinction early. A skill can improve the agent's reasoning. A package gives the agent, the shell, CI, and a control plane the same executable boundary.

Leadership frame

The job for Agentic DevOps leaders

Define boundaries

Separate agent advice from state-changing authority.

Package expertise

Part 1 · Interface problem

DevOps innovation feels stuck

  • Another wrapper around Terraform.
  • Another dashboard around plans.
  • Another queue, approval flow, policy layer, or YAML dialect.
  • Another system that still makes the low-level tool the public interface.
Another Terraform wrapper is not a new operating model.
Be clear that the target is not Terraform itself. The target is the operating model where low-level tool commands are treated as the user-facing product API.

  • provider schemas and conventions
This slide is the product-interface argument. Delivery teams and agents ask domain questions. Tool verbs answer implementation questions.

Agent

Part 2 · Skills

Skills got the key abstraction right

Package the knowledge of how to do something, give it a name, and make it reusable.

Named

A skill has identity. It can be invoked and discussed.

Reusable

The same procedure can be applied across tasks and contexts.

Contextual

It carries instructions, examples, and supporting context.

Give skills credit. The concept is useful because it recognizes that much knowledge is procedural, not just declarative documentation.
Procedural knowledge

Operations are procedural knowledge

  • How to provision a machine.
  • How to render environment-specific files.
  • How to configure DNS and SMTP.
  • How to run tools in the right order.
  • How to validate inputs and credentials.
  • How to describe current state.
  • How to safely delete or roll back.
  • How to produce useful artifacts and reports.

This is exactly the knowledge that tends to live in runbooks, scripts, wiki pages, and tribal memory.

Connect the skill concept to DevOps. Most operational knowledge is a sequence of guarded actions and interpretations, not a static config file.

Limits of skills

Skills stop at instructions

Agent-native

Useful inside an agent runtime, less useful outside it.

Weak reuse

No first-class library dependency model for shared operational code.

No contract

Instructions do not provide stable commands or authority boundaries.

No artifact model

Durable rendered files and reports belong in software.

The critique is not anti-skill. It is about placing skills at the right layer: guidance and reasoning, not the execution substrate.
Executable skill

A BigConfig package is a skill implemented as software

A skill says: “here is how to do this task.”
A BigConfig package says: “here is how to do this task as a runnable program.”
executable composable testable versioned shell-native library-backed
This is the product definition. BigConfig does not replace the idea of skills; it moves the execution part into a stable software package.
Software properties

Executable packages scale like software

Dependencies

Shared SDKs, renderer primitives, validators, and cloud abstractions.

Composition

Workflows assemble smaller tool steps into a domain lifecycle.

Testing

Pure reports and runner seams let tests avoid provisioning resources.

Versioning

Refs can be pinned to immutable commit SHAs.

Artifacts

Rendered files and reports survive outside the conversation.

APIs

The package exposes commands and reusable package-level functions.

Leaders should care about the software properties because they are what prevent duplication and drift as agentic procedures multiply.

Prompt pattern

Good agent instructions call the package

When working with this deployment:

1. Run `package validate` first.
2. If validation fails, inspect the report and propose a fix.
3. Run `package build` to inspect rendered artifacts.
4. Ask the operator before running state-changing verbs.
5. Never call Terraform, Helm, or cloud CLIs directly unless the package tells you to.
This slide makes the relationship concrete. The skill becomes a policy and reasoning layer. The package supplies the command surface.
Part 3 · Package contract

What is a BigConfig package?

A normal language package with one extra convention: a root run file that becomes the user-facing entrypoint.
  • Installable package code.
  • Packaged resources and templates.
  • A stable command surface.
  • Lifecycle workflows that can call any underlying tool.
Be precise: it is not a proprietary runtime. It is a package shape and launcher contract around normal language packages.
Polyglot shape

Target packages are polyglot

Clojure

deps.edn
resources in :paths
Babashka-friendly run

Python

pyproject.toml
[project].name
resources in wheel/sdist

TypeScript

package.json
name field
built JS and resources shipped

There are Python and npm implementations of bc-pkg; both can run Clojure target packages.

This corrects the old Clojure-only framing. Clojure remains a strong implementation path, but the current package spec is polyglot.
Launcher contract

The contract is intentionally small

One manifest

deps.edn, package.json, or pyproject.toml.

One run

The copied or symlinked user-facing entrypoint.

Installable code

Runtime files and resources must ship with the package.

Command surface

Arguments are forwarded exactly to the package.

The smallness is strategic. The launcher does not need to know the domain. The package owns the lifecycle semantics.
GitHub flow

How bc-pkg runs a GitHub package

User passes owner/repo@ref
→
Launcher resolves a 40-char SHA
Detect target language
→
Write native consumer manifest
Copy root run
→
Forward remaining argv
npx bc-pkg bigconfig-ai/once@typescript package validate
Emphasize pinning. A branch or tag is resolved once to a commit SHA, so the consumer has a stable dependency rather than a moving target.
Local mode

Local path mode is for live package development

Package author checkout
→
Local path dependency
→
Symlinked run
mkdir /tmp/once-consumer
cd /tmp/once-consumer
npx bc-pkg ../once/typescript package build

Switching between GitHub and local targets is intentionally a hard error.

Local mode matters for package authors. It supports a live edit/test loop while preserving the consumer directory boundary.
run handoff

The root run file is the user handoff

#!/usr/bin/env node
const DEFAULT_PROFILE = {
  profile: "default",
  params: { domain: "REPLACE_ME", package: "default" },
};
const { main } = await import("my-package/dist/src/cli.js");
main(process.argv.slice(2), DEFAULT_PROFILE);
The copied run file lands in a user's working directory. It should contain safe placeholders, not credentials.
The run file is intentionally small. It forwards argv and supplies a safe default profile or options map that the user can edit.
Lifecycle

The common lifecycle vocabulary

validate
build
create
describe
delete
validatePre-flight checks and safe reports.
buildRender artifacts into .dist/ without applying changes.
createCreate or reconcile real resources.
describeReport current state after provisioning.
deleteTear down resources behind explicit safety rules.
Present these as the minimal shared vocabulary, not a complete list of all possible domain operations.
Domain verbs

The package can expose the verbs the domain needs

cost-analysis backup restore rollback upgrade rotate-keys audit migrate
Forcing every operational question through apply is not simplicity. It is a lack of vocabulary.
This is where a package becomes a product interface. The public verbs should match the lifecycle of the thing being operated.
Workflow engine

Workflows compose named steps

opts map
→
step
→
step
→
opts map
  • Reserved engine keys are namespaced strings like big-config/exit and big-config.workflow/params.
  • Subworkflows isolate nested lifecycle execution.
  • Shell command execution goes through a runner seam.
Keep this technical but simple. The important property is that workflows are composable programs, not opaque scripts.
Profiles

Profiles and params make packages reusable

export BC_PAR_DOMAIN="example.com"
export BC_PAR_PROVIDER_BACKEND="r2"
export BC_PAR_COMPUTE_PREVENT_DESTROY="false"
  • Params use kebab-case strings that match template variables.
  • BC_PAR_* overrides uppercase keys and replace hyphens/dots with underscores.
  • Profiles compose smaller provider and application maps.
Explain parameter flow as part of the package contract. The same package can be reused across environments without changing the package code.
Artifacts

Templates produce durable artifacts

packaged resources
→
renderer
→
.dist/
  • Templates live in packaged resources such as src/resources/.../tools/.
  • Rendered files can be inspected before mutation.
  • Artifacts survive outside the agent conversation and can be reviewed by humans or CI.
Durable artifacts are a major difference from prompt-only workflows. The agent can inspect real generated files rather than merely trust text in a conversation.
Testability

The execution layer must be testable

Pure reports

Validation and describe builders accept injected dependencies.

Runner seam

Tests can swap real process execution for a fake runner.

Deterministic build

Rendered artifacts can be compared in `.dist/`.

If the package is the boundary for agentic operations, the package itself must be reviewable and testable.

This is for leaders: require package authors to make the command surface testable. Otherwise “agent-safe” is just a label.
Part 4 · Once

Once is an infrastructure package, not a Terraform folder

What it owns

  • Profiles and params.
  • Templates and rendered artifacts.
  • Workflow steps and plugins.
  • Lifecycle commands.

What it composes

  • OpenTofu/Terraform stages.
  • DNS and SMTP workflows.
  • Ansible-local and Ansible.
  • Remote-state backend injection.
Use Once as the concrete example because the user requested it. The point is that Once contains multiple tools but exposes one package surface.
Once commands

Once exposes lifecycle commands

$ npx bc-pkg bigconfig-ai/once@typescript package validate $ npx bc-pkg bigconfig-ai/once@typescript package build $ npx bc-pkg bigconfig-ai/once@typescript package create $ npx bc-pkg bigconfig-ai/once@typescript package describe $ npx bc-pkg bigconfig-ai/once@typescript package delete

Same package contract; different authority requirements per verb.

Show the external interface first. The audience should see that everything behind these commands can be complex while the public contract remains small.
Once pipeline

package create is a six-stage workflow

→
tofu-dns

The user does not need to orchestrate these stages manually. The package owns the workflow.
Explain that the pipeline illustrates why `terraform apply` is too low-level as a public interface. The domain operation spans multiple tools and state transitions.
Once params

Once threads parameters through the workflow

profile params
→
BC_PAR_* overrides
earlier Tofu outputs
→
later render and tool steps
rendered templates
→

Parameter flow is where many shell scripts become fragile. In a package, it is part of the explicit workflow model.
Build before mutation

package build renders before applying

$ npx bc-pkg bigconfig-ai/once@typescript package build # inspect generated artifacts $ find .dist -maxdepth 3 -type f
  • No real infrastructure mutation is required to inspect the package output.
  • Agents can summarize rendered artifacts before asking for authority.
  • CI can compare deterministic build output.
Build is the bridge between reasoning and action. It gives the agent something concrete to inspect without needing write credentials.
Demo prompt

Agent-ready prompt for Once validation

- run npx bc-pkg bigconfig-ai/once@typescript package validate
- inspect the validation report
- if it fails, explain the likely cause and propose the smallest fix
- do not run create or delete without operator approval
The agent receives a concrete command and a clear authority boundary.
This is not a live demo slide; it is the exact form of a prompt a leader can standardize. The agent is being directed to the package contract.
Demo command

Shell command for artifact generation

$ npx bc-pkg bigconfig-ai/once@typescript package build

Human operator

Runs the same command locally and reviews generated files.

CI or agent

Runs the same command in a sandbox and reports differences.

One command surface across callers is the point. The package is not just agent tooling; the agent is one caller among many.
Author flow

Package authors use local mode

$ mkdir /tmp/once-dev-consumer $ cd /tmp/once-dev-consumer $ npx bc-pkg ../once/typescript package build # edit package source in ../once/typescript, then rerun

Local mode symlinks the root run file and writes native local-path dependencies.

This is important for package authoring. You can iterate locally without publishing, while testing the same launcher path users will exercise.
Part 5 · Safety

Authority boundary by verb

Safe for agent advice

validate, build, describe

Read-only or no-credential commands produce information and artifacts.

Requires explicit authority

create, delete, rollback, upgrade

State-changing commands should require human or policy-controlled approval.

This is the operating model. The package contract makes it possible to standardize which verbs agents may run automatically.
Credential model

Credentials follow the verb, not the tool

VerbTypical credential classAgent posture
buildNo credentialssandbox-friendly
validateNo or read-only credentialsagent-friendly
describeRead-only credentialsagent-friendly
createRead-write credentialsapproval required
deleteRead-write credentials + guardapproval required
The phrase “credentials follow the verb” is useful. It moves policy away from raw tools and toward domain operations.
Operators

Kubernetes operators proved the idea, then siloed it

The good part

Operational knowledge expressed as a program: watch, reconcile, encode lifecycle behavior.

The limit

The knowledge is naturally trapped inside the Kubernetes runtime boundary.

The package should be the operational boundary. It can call Kubernetes, but it should not require every caller to live inside Kubernetes.
This connects to leadership decisions. Operators are excellent for cluster-native problems, but many agentic workflows begin outside the cluster: laptop, sandbox, CI, or external control plane.
Leadership standards

What Agentic DevOps leaders should standardize

  • Required lifecycle verbs and safety classes.
  • Where artifacts live, usually .dist/.
  • How params and environment overrides are named.
  • How packages are pinned and updated.
  • Pure report builders for validation and describe.
  • Runner seams for external commands.
  • No credentials in source or copied run files.
  • Local package development flow and conformance tests.
This is the call to action for leaders: create organizational standards around package contracts, not around prompt style alone.
Adoption path

How to start

  1. Pick one painful operational workflow.
  2. Wrap it in a package command surface.
  3. Add validate, build, and describe before expanding mutation.
  4. Render artifacts into .dist/.
  5. Publish a pinned package ref.
  6. Teach agents to call the package, not the raw tools.
Make adoption incremental. A team does not need to rewrite its platform. It can start by wrapping one workflow behind a stable executable package contract.
