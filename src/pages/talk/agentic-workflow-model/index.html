Agentic DevOps

From monolithic scripts to agent-friendly operations

BigConfig — May 2026

The Maturity Spectrum

Four levels. Each adds capability and safety. Level 04 unlocks agentic DevOps.

LevelVerbsConfigAgent-safe
01ScriptNoneNo
02Script + ConfigExternal fileNo
03Create + DeleteNamed entry pointsRisky
04Validate + DescribeRead/state separationYes

Level 01 — Script

A single file that does everything.

Characteristics:
  • No configuration separation — values are hardcoded
  • Operator edits the script to change behaviour
  • No validation, no dry-run, no safety nets
  • One typo can delete production resources

Fragile, opaque, unrepeatable. The starting point, not the goal.

#!/bin/bash
REGION="us-east-1"
CLUSTER="prod"
aws ecs create-cluster --cluster-name "$CLUSTER" --region "$REGION"

Level 02 — Script + Config

The script reads a configuration file.

What changes:
  • Config in JSON, YAML, or EDN
  • Operator edits config, not the script
  • Script is reusable across environments
  • Secrets still often hardcoded
Still missing:
  • No named entry points
  • No validation step
  • No separation of concerns
  • Imperative, not declarative

Where most teams operate today. Better, but not agent-ready.

Level 03 — Create + Delete

The interface is split into two named verbs.

create — provision resources from configuration.
delete — tear down resources from configuration.

Progress: First step toward an API contract. Entry points are named and predictable.

Still imperative: No validation gate. No way to check before running.
Agent would need full credentials to use either verb — risky.

Level 04 — Validate + Describe

Two read-only verbs complete the interface. Agentic DevOps becomes possible.

validate read-only

Checks configuration correctness before create/delete. Deterministic, side-effect-free.

describe read-only

Reads current state of the world. Useful during incidents, drift detection, or audits.

The agent advises. The operator acts.

Why Level 04 Changes Everything

The core insight:
validate is the command the agent can run without risk.

It is deterministic, safe, and gives the agent a productive loop — without handing over the keys to production.

Autonomous on the read side. Gated on the write side.

Inside Validation

Validation is a bundle of safety gates. All must pass before create/delete.

GateWhat it checksFailure example
SchemaConfig is syntactically correctMissing required field, type mismatch
ToolingRequired tools are installedterraform not found on PATH
CredentialsCredentials present, valid, not expiredAWS session token expired
DomainResource-specific preconditionsDocker image tag doesn't exist in registry

Validation passes → trust that create/delete will likely succeed.
Validation fails → know exactly what is wrong before executing.

DevOps in One Sentence

Describe your desired state
and run a command to make it happen.

The question is: which command should the agent run?

The answer: validate — deterministic, safe, and productive.

Part 2

The Operating Model

Level 04 gives us the contract.
Here is how to operationalise it.

The Core Idea

Agentic DevOps is not about giving an agent the same power as the operator.

If the agent gets the same credentials, filesystem access, and production authority as the operator, it is no longer an assistant. It is an unbounded operator with a prompt interface.

The agent advises. The operator acts.

The practical pattern is different — it is made of small decisions that reinforce each other.

Start with the Sandbox

The entry point is one command:

npx bc-pkg bigconfig-ai/bc-pkg shell

Launches Babashka through npx → reads bb.edn → runs Docker → creates a disposable container sandbox.

The launcher and sandbox are the operating environment.
A BigConfig package is what you operate from inside that environment.

The Agent Loop

1️⃣ Agent runs validate — schema, tools, credentials
2️⃣ Agent runs describe — what does current state look like?
3️⃣ Agent compares desired vs actual — is there drift?
4️⃣ Agent recommends next step to operator
5️⃣ Operator reviews and decides:
— create if resources are missing
— delete if resources need cleanup
— Re-validate if something is wrong

The Golden Path

operator
  → launches sandbox with bc-pkg
  → starts pi.dev agent inside sandbox
  → provides read-only credentials only
  → asks agent to run describe/validate
  → receives recommended next step
  → operator decides and runs create/delete
"Use describe and validate to inspect the current state.
Explain what you found and suggest the next step.
Do not run create or delete."

Read-Only Credentials Are the Boundary

That one rule removes a large class of failures.

  • describe and validate can interact with the environment
  • create and delete cannot succeed from inside the sandbox
  • Operator's full credentials stay outside the sandbox

This is not about mistrusting agents. It is about using them in the right role.

An agent is very good at reading, comparing, and recommending. Production authority is a separate concern.

ForceCommand as Policy Enforcement

describe and validate often need to query external systems. That interaction must be narrow, explicit, and auditable.

┌─────────────┐     narrow CLI      ┌──────────────────┐
│  Agent in    │  ──────────────────→│  ForceCommand     │
│  sandbox     │  ←──────────────────│  (policy enforcer)│
│  (read-only) │       result        └──────────────────┘
└─────────────┘                            │
                                           ↓
                                    ┌──────────────────┐
                                    │  External system  │
                                    │  (AWS, K8s, etc.) │
                                    └──────────────────┘

Why Not MCP for This?

MCP

  • Full protocol server
  • Broad interface surface
  • Harder to audit
  • Overkill for 2 verbs

ForceCommand CLI

  • Narrow, explicit commands
  • Minimal surface area
  • Simple to audit
  • Enough for validate + describe

When the agent only needs 2 safe verbs, a full protocol server is more abstraction than you need.

Patterns to Follow

  • Run agents inside disposable Docker containers
  • Launch the sandbox with bc-pkg
  • Use BigConfig packages with a clear four-verb interface
  • Give the sandbox read-only credentials only
  • Use describe and validate for agent investigation
  • Ask the agent to recommend the next step
  • Keep create and delete with the operator
  • Use SSH ForceCommand CLIs as policy enforcement points

None of these ideas is complicated. That is the point.
The operating model should be boring enough to repeat.

Anti-patterns to Avoid

  • Agent runs directly on the operator's host
  • Agent has access to the operator's full credentials
  • Package does not separate read-only and state-changing verbs
  • Agent is asked to perform create or delete without operator awareness
  • Broad MCP server exposes infra operations that could be a small ForceCommand CLI

These are not theoretical problems. They are design choices.
The safer design is available.
