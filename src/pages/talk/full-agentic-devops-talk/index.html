The State of DevOps Today

Terraform + Ansible + Kubernetes + Helm + GitHub Actions…

Each tool has its own YAML DSL, its own CLI, its own quirks.

We're still in the Separation by Technology era.

Think about it: to deploy an app you touch Terraform HCL, Ansible YAML, Helm charts, GitHub Actions YAML, Dockerfiles… all in different repos, different formats.

The YAML Trap

"Any sufficiently complicated C or Fortran program contains an ad-hoc, informally-specified, bug-ridden, slow implementation of half of Common Lisp."
— Greenspun's Tenth Rule

DevOps has reinvented half of Lisp… in YAML.

Loops in HCL, conditionals in Helm templates, expressions in GitHub Actions —
all without a debugger, compiler, or proper test framework.

The "Merchant of Complexity"

Vendors profit from your internal inefficiency.

  • Proprietary black boxes you can't debug
  • Perpetual consulting for "minor adjustments"
  • Fragmented solutions that require their experts to integrate
  • High switching costs — once you're in, you're stuck

The antidote? Simple over easy. Own your infrastructure.

DevOps Maturity Levels

From monolithic scripts to agent-friendly operations

The Maturity Spectrum

Four levels. Each adds capability and safety. Level 04 unlocks agentic DevOps.

LevelVerbsConfigAgent-safe
01ScriptNoneNo
02Script + ConfigExternal fileNo
03Create + DeleteNamed entry pointsRisky
04Validate + DescribeRead/state separationYes

Level 01 — Script

A single file that does everything.

Characteristics:
  • No configuration separation — values are hardcoded
  • Operator edits the script to change behaviour
  • No validation, no dry-run, no safety nets
#!/bin/bash
REGION="us-east-1"
CLUSTER="prod"
aws ecs create-cluster --cluster-name "$CLUSTER" --region "$REGION"

Fragile, opaque, unrepeatable. The starting point.

Level 02 — Script + Config

The script reads a configuration file.

What changes:
  • Config in JSON, YAML, or EDN
  • Operator edits config, not the script
  • Script reusable across environments
Still missing:
  • No named entry points
  • No validation step
  • No separation of concerns

Where most teams operate today. Better, but not agent-ready.

Level 03 — Create + Delete

The interface is split into two named verbs.

create — provision resources from configuration.
delete — tear down resources from configuration.

Progress: First step toward an API contract. Entry points are named and predictable.

Still imperative: No validation gate. Agent would need full credentials — risky.

Level 04 — Validate + Describe

Two read-only verbs complete the interface. Agentic DevOps becomes possible.

validate read-only

Checks configuration correctness before create/delete. Deterministic, side-effect-free.

describe read-only

Reads current state of the world. Useful during incidents, drift detection, or audits.

The Four-Verb Contract

VerbTypeSafe for agentDefault actor
validateread-onlyYesAgent in sandbox
describeread-onlyYesAgent in sandbox
createstate changeSupervisedOperator
deletestate changeSupervisedOperator
The agent advises. The operator acts.

Why Level 04 Changes Everything

validate is the command the agent can run without risk.

Deterministic. Safe. Gives the agent a productive loop — without handing over the keys to production.

Autonomous on the read side. Gated on the write side.

"Describe your desired state and run a command to make it happen.
The question is: which command should the agent run?
The answer: validate."

Inside Validation

Validation is a bundle of safety gates. All must pass before create/delete.

GateWhat it checksFailure example
SchemaConfig is syntactically correctMissing required field, type mismatch
ToolingRequired tools are installedterraform not found on PATH
CredentialsCredentials present, valid, not expiredAWS session token expired
DomainResource-specific preconditionsDocker image tag doesn't exist

All gates pass → trust that create/delete will likely succeed.

What is BigConfig?

A Clojure/Babashka workflow & template engine for IaC automation.

Think of it as npm for infrastructure.

📦 Packages
versioned, composable units
🔒 Client-Side Locking
using Git tags
⚡ Babashka
no server, no daemon
🤖 Agent-Native
designed for LLMs

Architecture at a Glance

ConceptWhat it does
WorkflowState-driven engine threading an opts map through pluggable steps
RenderSelmer-based template engine (like deps-new, but for infra)
LockClient-side Atlantis — pessimistic locking via Git tags
StoreRedis-backed event-sourcing with ACID guarantees
SystemLifecycle management — alternative to Integrant
BigTofuClojure constructs for generating OpenTofu/Terraform HCL

The Three Environments

BigConfig bridges three distinct contexts with one language:

🐚 Shell🔄 REPL📚 Lib
bb once createInteractive debuggingEmbed in your control plane
CI/CD pipelinesInspect state at any stepOrchestrate from APIs
GitHub ActionsNo edit-coffee-fail loopsDeep automation

Same code, same functions. No rewrite when you move from CLI → API.

The Killer Feature: Invisible Build Step

alias tofu="bb render git-check lock exec git-push unlock-any -- tofu"

One alias replaces Atlantis + Atmos.

render → generate config git-check → verify clean
lock → acquire lock exec → run tofu
git-push → commit result unlock-any → release

On failure, lock stays, changes stay local. Safe by default.

Why Clojure?

  • Data-driven: packages are plain data maps — agents can read, modify, reason without parsing DSLs
  • Immutability: state threaded through steps is never mutated — perfect for debugging
  • Babashka: same Clojure, zero JVM startup penalty — runs like a shell script
  • REPL: freeze time at any workflow step, inspect values, iterate instantly

The Workflow Engine

At the heart: a state-driven engine threading an opts map through steps.

(->workflow {:first-step ::start
             :wire-fn (fn [step _]
                        (case step
                          ::start [do-thing ::end]
                          ::end   [identity]))
             :next-fn (fn [step next-step opts]
                        (choice {:on-success next-step
                                 :on-failure ::end
                                 :opts opts}))})

Every step receives and returns opts. Branch on exit code. No side-channel state.

Nested Options = No Name Collisions

Composite workflows use namespaced state.

;; Terraform output → Ansible input, via opts-fn
(defn opts-fn [opts]
  (let [ip (-> (shell {:dir (workflow/path opts ::tool/tofu)}
                      "tofu show --json")
               parse ip)]
    (assoc-in opts [::workflow/params :ip] ip)))

;; Workflow: tofu → ansible → ansible-local
(pipeline [::tool/tofu    ["render -- tofu apply -auto-approve"]
           ::tool/ansible ["render -- ansible-playbook main.yml" opts-fn]])

Swap Hetzner for AWS? Just change the provider. Downstream Ansible stays untouched.

Client-Side Locking (No Atlantis Needed)

Pessimistic locking via Git tags — no server, no daemon.

StepWhat happens
generate-lock-idHash of lock keys (env, region, resource)
create-tagCreate a Git tag with the lock ID
push-tagPush it — if someone else's tag exists, push fails
unlock-anyForce-release any lock (for emergencies)

Template Engine (Render)

Selmer-based, inspired by deps-new. Generate config files from data.

{:big-config.render/templates
 [{:template   "tofu"
   :target-dir ".dist/tofu-{{profile}}"
   :transform  [["tofu" :raw]
                ["templates" "tofu"]]}]}
  • Template files with {{ variables }} → rendered output
  • Custom delimiters for EDN: < > avoids Selmer conflicts
  • Whitespace control: {{- var -}}
  • Binary files bypass rendering (images, etc.)

The Build → Control Plane Upgrade Path

GitOps

git push
→ CI runs tofu apply
→ manual PR review
→ wait for Atlantis

Control Plane

;; 200 lines of Clojure
(defn create-user [opts]
  (handle! store {:op :create
                  :name "alice"})
  (tofu/apply opts))

Same Terraform code. No rewrite. Just wrap it in a control plane API.

Part 5

The Agentic Operating Model

Level 04 + BigConfig = safe agentic DevOps in practice

The Core Idea

Agentic DevOps is not about giving an agent the same power as the operator.

If the agent gets full credentials, filesystem access, and production authority, it is no longer an assistant. It is an unbounded operator with a prompt interface.

The agent advises. The operator acts.

Start with the Sandbox

The entry point is one command:

BB_EDN_REPO=bigconfig-ai/npm-bb npx @bigconfig/bb shell

Launches Babashka through npx → reads bb.edn → runs Docker → creates a disposable container sandbox.

The launcher and sandbox are the operating environment.
A BigConfig package is what you operate from inside that environment.

The Agentic Workflow

You describe the deployment in plain English. Your agent does the rest.

1 Write a plan.md in English

2 Agent reads it, asks clarifying questions, writes bb.edn

3 bb package create — your app is live

plan.md → bb.edn → Deploy

Example: deploying a web app to Hetzner

Deploy the ONCE application basecamp/fizzy using the Once BigConfig Package.

Once BigConfig Package: https://github.com/bigconfig-ai/once
Docker image: ghcr.io/basecamp/fizzy

Steps:
- make sure that Babashka is installed
- review the source code of Once BigConfig Package
  https://raw.githubusercontent.com/bigconfig-ai/once/refs/heads/main/CLAUDE.md
- create the bb.edn file
- run bb validate and iterate on failures

The agent produces a single bb.edn — no Terraform, no Ansible YAML, no Helm chart.

Configuration (bb.edn)

{:deps {io.github.bigconfig.ai/once {:git/url "https://github.com/bigconfig-ai/once"
                                 :git/sha "8ffbbc2e..."}}
 :tasks {:requires ([io.github.amiorin.once.package :as pkg])
         package {:doc "bb package create | bb package delete"
                  :task (pkg/once* *command-line-args*
                          {:big-config.render/profile "online"
                           :big-config.workflow/params
                           {:domain          "bigconfig.online"
                            :provider-compute "oci"
                            :oci-shape       "VM.Standard.A1.Flex"
                            :provider-dns    "cloudflare"
                            :provider-smtp   "resend"
                            ...}})}}}

Compute + DNS + SMTP. One config file. Three infrastructure domains.

What the Agent Doesn't Write

  • ❌ Terraform main.tf (hundreds of lines of HCL)
  • ❌ Ansible playbooks with hardcoded IPs
  • ❌ Kubernetes manifests or Helm values
  • ❌ Bash scripts gluing CLIs together

The agent composes packages. The package authors handle the "how."

The Agent Loop

1️⃣ Agent runs validate — schema, tools, credentials
2️⃣ Agent runs describe — what does current state look like?
3️⃣ Agent compares desired vs actual — is there drift?
4️⃣ Agent recommends next step to operator
5️⃣ Operator reviews and decides:
— create if resources are missing
— delete if resources need cleanup
— Re-validate if something is wrong

The Golden Path

operator
  → launches sandbox with @bigconfig/bb
  → starts pi.dev agent inside sandbox
  → provides read-only credentials only
  → asks agent to run describe/validate
  → receives recommended next step
  → operator decides and runs create/delete
"Use describe and validate to inspect the current state.
Explain what you found and suggest the next step.
Do not run create or delete."

Read-Only Credentials Are the Boundary

That one rule removes a large class of failures.

  • describe and validate can interact with the environment
  • create and delete cannot succeed from inside the sandbox
  • Operator's full credentials stay outside the sandbox

This is not about mistrusting agents. It is about using them in the right role.

ForceCommand as Policy Enforcement

describe and validate often need to query external systems. That interaction must be narrow, explicit, and auditable.

┌─────────────┐     narrow CLI      ┌──────────────────┐
│  Agent in    │  ──────────────────→│  ForceCommand     │
│  sandbox     │  ←──────────────────│  (policy enforcer)│
│  (read-only) │       result        └──────────────────┘
└─────────────┘                            │
                                           ↓
                                    ┌──────────────────┐
                                    │  External system  │
                                    │  (AWS, K8s, etc.) │
                                    └──────────────────┘

Why Not MCP for This?

MCP

  • Full protocol server
  • Broad interface surface
  • Harder to audit
  • Overkill for 2 verbs

ForceCommand CLI

  • Narrow, explicit commands
  • Minimal surface area
  • Simple to audit
  • Enough for validate + describe

When the agent only needs 2 safe verbs, a full protocol server is more abstraction than you need.

Patterns to Follow

  • ✅ Run agents inside disposable Docker containers
  • ✅ Launch the sandbox with @bigconfig/bb
  • ✅ Use BigConfig packages with a clear four-verb interface
  • ✅ Give the sandbox read-only credentials only
  • ✅ Use describe and validate for agent investigation
  • ✅ Ask the agent to recommend the next step
  • ✅ Keep create and delete with the operator
  • ✅ Use SSH ForceCommand CLIs as policy enforcement points

None of these ideas is complicated. The operating model should be boring enough to repeat.

Anti-patterns to Avoid

  • ❌ Agent runs directly on the operator's host
  • ❌ Agent has access to the operator's full credentials
  • ❌ Package does not separate read-only and state-changing verbs
  • ❌ Agent is asked to perform create or delete without operator awareness
  • ❌ Broad MCP server exposes infra operations that could be a small ForceCommand CLI

These are not theoretical problems. They are design choices. The safer design is available.

Key Takeaways

  1. DevOps is stuck in the pre-React era — separate by technology, not concerns
  2. Level 04 (Validate + Describe) is the agentic baseline — read-only verbs for agents, state-changing for operators
  3. AI doesn't write bad Terraform — it lacks abstractions
  4. BigConfig is npm for infrastructure — compose packages, don't write scripts
  5. Clojure all the way down: Shell → REPL → Lib without rewrites
  6. Sandbox + read-only creds + ForceCommand = safe agentic DevOps
