BigConfig Polyglot Package Specification

A language-neutral package model for BigConfig: packages can be implemented in Clojure, TypeScript, Python, and other ecosystems, while sharing templates and guaranteeing that render produces the same .dist artifacts byte-for-byte for a given package version.

Overview #

BigConfig started as a Clojure/Babashka infrastructure package system. This specification generalizes the package model so package authors can ship the same BigConfig package in multiple language ecosystems without forcing every author or user to adopt Clojure.

The model is intentionally siloed: Clojure implementations compose with Clojure implementations, TypeScript implementations compose with TypeScript implementations, and Python implementations compose with Python implementations. Cross-language runtime composition is not required.

Core promise Same package version, same shared resources, different language implementations, identical .dist after package render.

Language-native implementations

Each ecosystem exposes an idiomatic package and CLI entry point.

Shared templates

Every implementation embeds the same shared template/configuration files.

Version synchronization

A package version means the same rendered artifacts across supported ecosystems.

Render conformance

Release CI compares generated .dist directories byte-for-byte.

Goals #

  1. Enable cross-language BigConfig package authorship. Package authors should be able to implement packages in Clojure, TypeScript, Python, or another supported language.
  2. Preserve one package mental model. Users should recognize the same verbs and command shape in every ecosystem.
  3. Guarantee rendered artifact compatibility. For a package version, every supported implementation must produce the same .dist output after package render.
  4. Let language implementations remain idiomatic. Workflows are implemented in each language, not generated from a universal workflow DSL.
  5. Make releases auditable. The release gate proves equivalence through deterministic rendering and byte-for-byte directory comparison.

Non-goals #

  • No cross-language package composition. A TypeScript package does not compose with a Clojure package at runtime.
  • No universal workflow DSL. Each language implementation defines its own workflow in code.
  • No cross-language conformance for every verb. Only package render has a byte-for-byte compatibility requirement.
  • No mandatory Clojure implementation. Every package version declares exactly one reference ecosystem, and it can be any supported ecosystem.
  • No global default reference ecosystem. Clojure is not the preferred default by specification.

Repository layout #

A polyglot BigConfig package is a monorepo. The shared/ directory is the source of truth for metadata and common resources. Each language folder contains a separate implementation. 

once/
├── shared/
│   ├── bigconfig.yaml
│   └── io/
│       └── github/
│           └── bigconfig-ai/
│               └── once/
│                   ├── tofu-compute/
│                   ├── tofu-dns/
│                   ├── tofu-smtp/
│                   └── ansible/
├── clojure/
│   ├── bb.edn
│   ├── deps.edn
│   └── src/...
├── typescript/
│   ├── package.json
│   ├── src/...
│   └── tsconfig.json
└── python/
    ├── pyproject.toml
    └── src/...
Publishing rule Package publishing must copy or embed the contents of shared/ into each language-specific package distribution.

shared/bigconfig.yaml #

shared/bigconfig.yaml contains package metadata only. It does not define the package workflow. Workflows are implemented independently in each language. 

schema: 1
owner: bigconfig-ai
repo: once
name: once
version: 0.1.0

reference:
  ecosystem: clojure

ecosystems:
  clojure:
    package: io.github.bigconfig-ai/once
    command: once
  typescript:
    package: bigconfig-once
    command: bigconfig-once

Shared resources #

Shared templates and configuration files are located by convention. A template path is always: 

io/github/<owner>/<repo>/<tool-workflow-name>/...

The <tool-workflow-name> segment identifies the tool workflow that consumes the resource. 

shared/io/github/bigconfig-ai/once/tofu-compute/...
shared/io/github/bigconfig-ai/once/tofu-dns/...
shared/io/github/bigconfig-ai/once/tofu-smtp/...
shared/io/github/bigconfig-ai/once/ansible/...
Convention over metadata bigconfig.yaml does not need to list every template path. Implementations resolve resources from owner, repo, and the tool workflow name.

Ecosystems #

The specification distinguishes between the logical package name, ecosystem package name, and CLI command name.

NameExampleMeaning
Logical package nameonceThe BigConfig package identity.
Ecosystem package namebigconfig-onceThe package name in npm, PyPI, Maven/Git deps, etc.
CLI command namebigconfig-onceThe command users execute through the ecosystem runner.

ecosystems lists only ecosystems supported for the current package version. If an implementation lags behind, it can be removed from the supported set for that version.

Package verbs #

Every supported implementation exposes the same package verbs:

VerbRequiredCross-language output contractDescription
renderrequiredbyte-for-byte .distOrchestrates tool workflow render steps and writes configuration files.
validaterequiredpackage/language-specificChecks package inputs, generated files, credentials, or external state.
describerequiredpackage/language-specificReports current state or relevant package information.
createrequiredpackage/language-specificProvisions or mutates resources.
deleterequiredpackage/language-specificDestroys or removes resources.
Important validate, describe, create, and delete share names and conceptual meaning, but their output is intentionally package/language-specific in this version of the specification.

CLI contract #

Each ecosystem uses its native runner, but the user-facing command shape is consistent: 

bb <package-command> <verb>
npx <package-command> <verb>
uvx <package-command> <verb>

Examples

bb once render
bb once create

npx bigconfig-once render
npx bigconfig-once create

uvx bigconfig-once render
uvx bigconfig-once create

The actual command names are declared in shared/bigconfig.yaml under each ecosystem.

Workflows #

A package workflow is a composition of tool workflows. The package render verb is an orchestration render: it invokes the actual render behavior of tool workflows. 

package render
  -> tofu-compute render
  -> tofu-dns render
  -> tofu-smtp render
  -> ansible render

Workflows are implemented in code inside each language implementation. They are not declared in bigconfig.yaml.

Tool workflow

Does the real work for a concrete step, including rendering templates into .dist.

Package workflow

Orchestrates tool workflows into package-level verbs such as render and create.

Template language #

Shared templates use a standardized template language. Clojure Selmer is the reference implementation for template semantics.

Portability requirement Non-Clojure renderers must be compatible with the Selmer features used by the shared templates. In practice, compatibility is proven by the render conformance test.

The practical implication is that whitespace, conditionals, filters, path rendering, and formatting must be deterministic across languages for the subset of Selmer used by the package.

Render contract #

Package render is the only verb with a cross-language byte-for-byte compatibility contract.

  1. For the same package version and same inputs, every supported implementation must render the same .dist directory.
  2. Equality means byte-for-byte equality of the generated files.
  3. File contents, paths, newlines, whitespace, serialized map ordering, and generated names must match.
  4. Only ecosystems listed in shared/bigconfig.yaml are part of the conformance set for that version.

Reference implementation #

Every package version declares exactly one reference implementation in shared/bigconfig.yaml. The reference implementation generates the canonical .dist for that package version. 

reference:
  ecosystem: clojure

The reference ecosystem can change between versions, and Clojure is not mandatory. 

# Version 0.1.0
reference:
  ecosystem: clojure

# Version 0.2.0
reference:
  ecosystem: typescript
Rule If an implementation is listed under ecosystems, it must match the reference implementation's rendered .dist output for that version.

Release gate #

The release rule is:

Release rule Generate .dist from the declared reference implementation. Every other supported implementation must match it byte-for-byte. If an implementation fails, fix it or remove that ecosystem from the supported set for that version.

Package versions are synchronized across supported ecosystems. If once version 0.1.0 is published for Clojure and TypeScript, both implementations must render the same configuration files for 0.1.0.

CI example #

A release CI pipeline should read shared/bigconfig.yaml, determine the reference ecosystem, run package render, then compare every other supported implementation against the reference. 

#!/usr/bin/env bash
set -euo pipefail

rm -rf /tmp/bigconfig-render
mkdir -p /tmp/bigconfig-render/reference
mkdir -p /tmp/bigconfig-render/typescript

# Example where Clojure is the declared reference.
(
  cd clojure
  bb once render
  cp -a .dist/. /tmp/bigconfig-render/reference/
)

(
  cd typescript
  npx bigconfig-once render
  cp -a .dist/. /tmp/bigconfig-render/typescript/
)

diff -ruN \
  /tmp/bigconfig-render/reference \
  /tmp/bigconfig-render/typescript

A real implementation should generate this matrix from shared/bigconfig.yaml instead of hardcoding ecosystem names.

once MVP #

The first package to prove the model is once. The MVP supports Clojure and TypeScript.

DimensionDecision
Packageonce
Initial ecosystemsclojure, typescript
Initial commandsbb once <verb>, npx bigconfig-once <verb>
Required compatibilityrender produces byte-for-byte identical .dist
Primary userPackage authors creating cross-language BigConfig packages

MVP success criteria

  1. shared/bigconfig.yaml exists and declares Clojure + TypeScript ecosystems.
  2. Shared resources use io/github/bigconfig-ai/once/<tool-workflow>/....
  3. Clojure package bb once render generates .dist.
  4. TypeScript package npx bigconfig-once render generates .dist.
  5. CI compares both directories and blocks release on differences.

Risks and mitigations #

RiskWhy it mattersMitigation
Template drift Different renderers may interpret templates differently. Use Selmer-compatible semantics and prove compatibility with .dist diffs.
Whitespace differences Byte-for-byte equality is sensitive to newline and whitespace behavior. Normalize renderer behavior and include newline conventions in implementation tests.
Workflow drift Workflows are implemented independently in each language. Release gate catches drift for render; document tool workflow names carefully.
Publishing complexity Versions must stay synchronized across ecosystems. Automate release from the monorepo and embed shared/ during packaging.
Spec fragmentation Packages may diverge if conventions are optional. Keep bigconfig.yaml small, normative, and enforced by CI.

Glossary #

BigConfig package specification
The language-neutral rules for metadata, shared resources, package verbs, and render conformance.
Language silo
An isolated ecosystem implementation. Packages do not compose across silos.
.dist
The generated configuration directory produced by package render.
Byte-for-byte equality
Exact equality of generated file paths and file contents, not just semantic equivalence.
Supported ecosystem
An ecosystem listed in shared/bigconfig.yaml for the current package version.
Reference ecosystem
The one ecosystem declared as canonical for generating reference .dist output for the version.
