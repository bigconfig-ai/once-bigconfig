## Goal

Create a publish-ready **tutorial-style** website article, a LinkedIn post, and visual
assets showing readers how to use the three Claude Code skills that scaffold minimal,
launcher-conformant BigConfig packages in:

- TypeScript
- Python
- Clojure

Core thesis:

> BigConfig packages are executable operational skills, and now agents can scaffold a
> correct starter package in the language you already use: TypeScript, Python, or
> Clojure.

The tutorial should connect three layers:

1. **Claude Code skills** teach the agent how to create a package correctly.
2. **Generated BigConfig packages** are normal language packages with `validate` and
   `build` verbs, tests, resources, and a launcher-friendly `run` file.
3. **`bc-pkg` / package spec** make those packages runnable by humans, agents, shells,
   and CI.

## Blog article shape

1. **Open with the tutorial goal**
   - Show how to install and try the three BigConfig package-creation skills in Claude
     Code.
   - Name the three languages immediately: TypeScript, Python, and Clojure.
   - Make clear these are not demo snippets; they scaffold the smallest real package that
     follows the package contract.

2. **Explain why this matters**
   - Writing an executable operational package used to have too much boilerplate.
   - Agents are good at growing code, but they need a correct starting shape.
   - The skills package the conventions so authors do not start from a blank directory.
   - Mention that these skills were created and verified through agentic development:
     generate a package, run the language-native tests, run `package validate`, run
     `package build`, then fix the template until it passes.

3. **Connect to the earlier "skills vs packages" framing**
   - A skill is agent-native procedural knowledge.
   - A BigConfig package is shell-native executable procedural knowledge.
   - These skills create packages: the skill teaches the agent, the package gives humans,
     agents, CI, and scripts a durable command interface.

4. **What each generated package includes**
   - One language-native manifest:
     - `package.json`
     - `pyproject.toml`
     - `deps.edn`
   - A root launcher-friendly `run` file.
   - A single `hello` render stage.
   - `package validate` and `package build`.
   - Packaged resources/templates.
   - Tests.
   - `BC_PAR_*` parameter override support.
   - A path to `bc-pkg` compatibility.

5. **Why three languages**
   - BigConfig packages should be normal software packages.
   - Platform teams can author in the language that fits their ecosystem.
   - TypeScript, Python, and Clojure starters share the same outside contract while using
     idiomatic internals.

6. **Show exact installation and usage**
   - Include the Claude Code skill installation/symlink commands.
   - Show the conceptual workflow:
     - choose a language skill
     - scaffold a package
     - run install/tests
     - run `package validate`
     - run `package build`
   - Show the language-specific verification commands so readers know what success looks
     like.

7. **BigConfig package spec tie-in**
   - The skills encode the package spec into working starter code.
   - The important boundary is not internal file layout; it is the outside contract:
     root manifest, root `run`, resources, lifecycle verbs, reproducible launcher use.

8. **Close with CTA**
   - Primary CTA: try the skills.
   - Secondary links: read the Package Spec and the skills-vs-packages article.
   - Use the starter as a seed and grow it into your real operational package.

## Editorial guardrails

- Do not imply that skills replace BigConfig packages. The skill is the authoring aid;
  the package is the executable artifact.
- Do not imply the generated starter is a full production package. It is intentionally
  minimal: one `hello` stage, `validate`, `build`, tests, and a correct package shape.
- Do not over-explain internal implementation details from plans 23/24; keep the article
  user-facing.
- Keep the package-spec boundary precise: one supported manifest, root `run`, installable
  resources, lifecycle verbs, and launcher compatibility.
- Mention `bc-pkg` only as the launcher/package-manager contract, not as required to run
  the starter locally during authoring.
- Use kebab-case command names and file names exactly as the skills use them.
- Avoid third-party language logos unless approved assets are available; use text badges
  for TypeScript/Python/Clojure.
- Keep the LinkedIn post concise and avoid raw URLs in the main body; put links in the
  suggested first comment.
