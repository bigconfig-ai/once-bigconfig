## Core positioning

### Shared ideas with the source post

- Do **not** reinvent Terraform/OpenTofu, DNS APIs, cache APIs, Ansible, or cloud CLIs.
- Orchestrate the existing tools behind a higher-level operational interface.
- Treat outputs from one stage as inputs to the next stage instead of relying on manual copy/paste or old shell scripts.
- Keep workflows in version control.
- Make infrastructure automation modular enough that the consumer of a value does not need to know every provider-specific implementation detail.

### BigConfig distinction

BigConfig pushes the same pattern one layer further:

1. **Code-first**
   - A workflow is a package/program, not only YAML.
   - Package authors can use real language features, tests, pure report builders, validation, template rendering, and normal dependency management.
   - Terraform/OpenTofu remains an implementation detail inside package lifecycle verbs.

2. **Local-first**
   - The package can run from a laptop, CI, shell, agent session, or future control plane.
   - Rendered artifacts are produced locally under `.dist/` before native tools run.
   - State stays with the tools that own it, e.g. OpenTofu/Terraform remote state.

3. **Agent-first**
   - Agents should call stable package verbs such as `package validate`, `package build`, `package create`, `package describe`, and `package delete`.
   - Agents should not need to become mediocre operators of Terraform, Cloudflare, Ansible, cache purges, and provider naming conventions all at once.
   - A package boundary gives agents a smaller, safer, more domain-oriented command surface.

## BigConfig concepts to emphasize

- **Packages, not loose scripts**: the operational workflow has a root `run` file, lifecycle verbs, package resources, templates, params, and tests.
- **Tool orchestration, not tool replacement**: BigConfig wraps Terraform/OpenTofu, Ansible, APIs, and CLIs rather than competing with them.
- **Terraform outputs as a handoff ABI**: each stage can expose normalized outputs that become params for later stages.
- **Decoupling provider names from consumers**: the DNS stage should consume something like `public-ip`, not care whether Hetzner called it `ipv4_address`, OCI called it something else, or the value came from an existing host.
- **Parametric hidden implementation**: `main.tf` can be rendered from templates and selected by profile/provider so users interact with params and package verbs, not raw provider files.
- **Concrete Once example**: `once package create` already composes stages such as `tofu`, `tofu-smtp`, `tofu-dns`, `tofu-smtp-post`, `ansible-local`, and `ansible`.

## Proposed article outline

1. **Hook: Terraform ends where Day 2 begins**
   - `apply` is necessary, but it is rarely the end of the workflow.
   - IPs change, DNS records need updates, caches need purging, app config needs rendering, teams need notifications.

2. **The good instinct: orchestrate instead of reinventing**
   - The source pattern is right: keep Terraform and run follow-up work immediately after.
   - The problem is not Terraform; the problem is making the orchestration layer another low-level public interface.

3. **The comparison: YAML workflow vs infrastructure package**
   - YAML workflow approach: useful for central orchestration, plugins, logs, approvals, and run history.
   - BigConfig package approach: code-first package, local-first execution, agent-first lifecycle verbs.
   - Keep the comparison rational and generic, not hostile.

4. **Where BigConfig draws the boundary**
   - The workflow should be an infrastructure package.
   - The package exposes lifecycle verbs and hides the tool choreography.
   - Use TypeScript examples for package concepts and snippets.

5. **Terraform output as a modular handoff**
   - Normalize provider-specific outputs into stable package params.
   - Example: later DNS/template stages consume `public-ip`; they do not care how the provider named that output.

6. **Templates hide parametric implementation details**
   - Render `main.tf`, inventories, DNS config, app config, etc. from params and profiles.
   - Users and agents work with package params, not a forest of provider-specific files.

7. **Code-first, local-first, agent-first**
   - Code-first: TypeScript code, tests, package dependencies, report builders.
   - Local-first: no mandatory hosted control plane; runs from laptop/CI/agent; renders artifacts locally.
   - Agent-first: stable verbs and validation give agents safer primitives than low-level tool commands.

8. **Concrete Once example**
   - Use `once package create` as the example pipeline.
   - Include the stage sequence: `tofu → tofu-smtp → tofu-dns → tofu-smtp-post → ansible-local → ansible`.
   - Explain how outputs feed later stages.

9. **Conclusion / CTA**
   - Keep Terraform.
   - Stop making Terraform the whole interface.
   - Package the Day 2 workflow.
   - Primary CTA: BigConfig homepage (`/`).
