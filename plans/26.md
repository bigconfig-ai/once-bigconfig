## Review / diagnosis

The original comparison is strong because it exposes a boundary that raw
Terraform often misses:

> In vanilla Terraform, using the infrastructure and developing the
> infrastructure package often look like the same workflow. In BigConfig, they
> are different workflows for different roles.

This should be the center of the article. The argument is not simply that
BigConfig runs more commands or wraps Terraform. The argument is that BigConfig
creates two interfaces:

1. **Consumer interface** — a package instance that exposes lifecycle verbs such
   as `package validate` and `package create`.
2. **Author interface** — the package source code, where platform engineers edit
   templates/workflows and iterate by rendering artifacts and running underlying
   tools such as OpenTofu.

That separation gives each role a smaller, safer surface:

- Delivery teams change instance-level intent instead of editing the platform
  package source.
- Platform teams keep Terraform/OpenTofu, Ansible, Helm, cloud APIs, etc. inside
  the package.
- Agents get explicit verbs instead of being asked to infer whether raw
  Terraform commands are safe.
- The source repository becomes an implementation detail for consumers.

## Goal

Write a blog article that turns the comparison into a clear explanation of why
infrastructure packages need separate **usage** and **development** workflows.

Core thesis:

> The important difference between raw Terraform and BigConfig is not that
> BigConfig can run Terraform. It is that BigConfig separates using an
> infrastructure package from developing the package source.

Secondary thesis:

> With raw Terraform, `git clone`, edit files, and run Terraform is both the
> consumer workflow and the author workflow. With BigConfig, consumers operate a
> package instance through lifecycle verbs, while package authors iterate on the
> package source through render/tool loops.

Relevant facts to reuse carefully:

- `bc-pkg` bootstraps a consumer directory, pins a GitHub package ref to a
  40-character commit SHA, copies the package `run` file, writes a native
  manifest, and forwards later commands to the pinned package.
- Local path mode exists for live package development, but it must be run from a
  separate consumer directory; it does not target the package source directory
  itself.
- The recommended lifecycle vocabulary is `package validate`, `package build`,
  `package create`, `package describe`, and `package delete`.
- `package create` does **not** implicitly call `validate`; users can run
  `package validate` first or chain `package validate create` when supported.
- `package build` renders artifacts into `.dist/` without applying changes.
- Individual tool runners need `render` first, for example package CLIs can
  expose commands like `tofu render tofu:init tofu:apply:-auto-approve` through
  their runtime entrypoint.
- BigConfig CLI parsing recognizes `render` and `exec`; commands after `--` are
  consumed by the exec step, and `exec` can be added explicitly or implicitly by
  the parser.
- Package source contains installable code, a root `run` file, templates and
  resources. Rendered output belongs in `.dist/` and is generated, not source.
- The recent article `from-terraform-apply-to-infrastructure-programs.mdx`
  already argues that infrastructure packages should expose richer verbs than
  `plan/apply/destroy`. Plan 26 should avoid repeating that article and instead
  focus on the **consumer repo vs source repo** split.

Use this contrast:

| Question | Vanilla Terraform | BigConfig package model |
|---|---|---|
| What does a consumer clone? | Often the same Terraform source repo the platform team maintains. | A package instance/consumer repo, or an empty directory initialized by `bc-pkg`. |
| What does a consumer edit? | Terraform variables, modules, provider config, sometimes real implementation files. | Instance-level intent: `run`, profile/params, env overrides, app list. |
| What does a consumer run? | `terraform validate`, `terraform plan`, `terraform apply`. | `package validate create`, optionally `package build`/`describe` first. |
| What does an author clone? | The same repo. | The package source repo. |
| What does an author edit? | The same Terraform source. | Workflow code, templates, packaged resources, validation/report logic. |
| What does an author run? | The same Terraform commands. | Render/tool loops such as `npx . tofu render tofu:init -- tofu plan` (TypeScript/npm) or equivalent local entrypoints (`uvx . ...`, `bb run ...`), package tests, `package build`. |
| Where is Terraform/OpenTofu? | The public interface. | An implementation detail inside the package. |

## Proposed article outline

1. **Open with the overloaded Terraform workflow**
   - In many teams, the workflow for using infrastructure is the same as the
     workflow for developing infrastructure: clone repo, edit files, run
     Terraform.
   - That is familiar, but it is not a real product interface.

2. **Name the two jobs**
   - Using a package: express intent for one instance and run lifecycle verbs.
   - Developing a package: change the reusable source code, templates,
     validation, reports, and tool orchestration.
   - These jobs need different repositories and different commands.

3. **Vanilla Terraform collapses consumer and author**
   - The same repo is often both package source and deployment instance.
   - The consumer must understand implementation details: modules, variables,
     providers, state, plan/apply semantics.
   - This creates accidental authorship: users can become package developers just
     to make a normal app-level change.

4. **BigConfig splits instance repo from source repo**
   - The instance repo is small, app/team-owned, and points to a pinned package.
   - The source repo is where package authors change workflows/templates.
   - `bc-pkg` can initialize the consumer directory and pin the source package.

5. **Consumer flow: operate the instance**
   - Clone the package instance repo, or initialize one with `bc-pkg`.
   - Edit instance-level intent: params/profile/app list/`run` placeholders or
     `BC_PAR_*` env vars.
   - Run the chained `package validate create` workflow when ready, so
     validation passes before the state-changing step runs.
   - Optional: run `package build` to inspect `.dist/` without applying.

6. **Author flow: develop the package**
   - Clone the package source repo.
   - Edit code, templates, resource packaging, validation, and reports.
   - Render artifacts and run OpenTofu/Ansible/tool commands from the rendered
     output.
   - Test the package through both local-path and pinned consumer flows before
     publishing.

7. **Why this matters for platform teams**
   - Platform teams keep Terraform/OpenTofu and other tools.
   - They stop making raw tool commands the delivery-team interface.
   - The package source can be reviewed like code and versioned like software.

8. **Why this matters for delivery teams and agents**
   - Delivery teams do not need to learn every low-level implementation detail.
   - Agents get explicit safe verbs (`validate`, `build`, `describe`) and
     explicit state-changing verbs (`create`, `delete`).
   - The package instance is a better working directory for an agent than the
     reusable source package.

9. **Close**
   - Terraform/OpenTofu can remain inside the package.
   - Users should operate packages; authors should develop packages.
   - The interface is the lifecycle contract, not the source tree.

## Command examples to use

### Vanilla Terraform usage/development collapse

```bash
git clone git@github.com:company/platform-terraform.git my-app-infra
cd my-app-infra
# edit .tf / .tfvars / module inputs
terraform init
terraform validate
terraform plan
terraform apply
```

### BigConfig consumer flow from an existing instance repo

```bash
git clone git@github.com:company/my-app-infra.git
cd my-app-infra
# edit run / params / env overrides / app list
npx bc-pkg package validate create
```

### BigConfig consumer flow from first bootstrap

```bash
mkdir my-app-infra
cd my-app-infra
npx bc-pkg company/app-platform@main package validate
# edit the copied run file / params for this instance
npx bc-pkg package validate create
```

If both launcher examples are useful in the tutorial, mirror the bootstrap with
`uvx`:

```bash
uvx bc-pkg company/app-platform@main package validate
uvx bc-pkg package validate create
```

### BigConfig package-author flow

```bash
git clone git@github.com:company/app-platform.git
cd app-platform
# edit package source code / templates / resources
npx . tofu render tofu:init -- tofu plan
```

Clarify in the article that `npx . tofu ...` is the TypeScript/npm package
source form. Also include language equivalents:

```bash
uvx . tofu render tofu:init -- tofu plan
bb run tofu render tofu:init -- tofu plan
```
