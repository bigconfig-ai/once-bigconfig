## Goal

Create a blog article, blog cover image, inline diagram, and LinkedIn draft arguing that DevOps
is stuck because the industry still exposes infrastructure as low-level tool
commands and configuration files, while the agent era makes it practical to ship
infrastructure knowledge as executable packages/programs.

Core thesis:

> The next DevOps abstraction is not another wrapper around `terraform plan`,
> `apply`, and `destroy`. It is a package that is itself a program: runnable by
> an agent, a shell, CI, or a control plane, and free to expose the verbs the
> domain actually needs.

Secondary thesis:

> Platform teams can keep Terraform, Helm, Ansible, Kubernetes operators, and
> their other expert tools inside the package. Delivery teams should receive a
> higher-level operational program with verbs such as `validate`, `describe`,
> `create`, `delete`, `cost-analysis`, `rollback`, `backup`, and `upgrade`.

## Source material reviewed

Primary source files:

- `src/pages/manual.html`
- `src/pages/package-spec.html`

Relevant facts from `manual.html`:

- BigConfig is presented as a stack:
  - `bc-pkg` launcher
  - Once package CLI
  - BigConfig SDK/workflow/render engine
  - Selmer templates
- `bc-pkg` pins a target package from GitHub to a 40-character commit SHA,
  copies its root `run` file, writes a native manifest, and forwards commands to
  the target.
- `bc-pkg` has Python and TypeScript launcher implementations; there is no
  Clojure launcher implementation, but both launchers can run Clojure targets.
- Once exposes lifecycle commands:
  - `package validate`
  - `package describe`
  - `package build`
  - `package create`
  - `package delete`
  - chained commands such as `package validate create`
- `create` does not call `validate` automatically. Validation and describe are
  explicit workflow steps, which supports authority separation.
- Once’s `create` pipeline composes multiple tools/stages: Tofu, DNS, SMTP,
  Ansible-local, and Ansible.
- Profiles, `BC_PAR_*` overrides, templates, plugins, and deterministic build
  artifacts show the package is more than a CLI wrapper.

Relevant facts from `package-spec.html`:

- The BigConfig Package Spec is a friendly implementation guide for repositories
  that `bc-pkg` can pin, initialize, and run.
- The launcher contract is intentionally small:
  - exactly one root manifest: `deps.edn`, `package.json`, or `pyproject.toml`
  - one root `run` file
  - installable package code/resources
  - a stable command surface
- GitHub mode pins refs to SHAs; local path mode supports live development.
- Generated consumer files are language-native:
  - Clojure: `run`, `deps.edn`, `bb.edn`
  - TypeScript: `run`, `package.json`
  - Python: `run`, `pyproject.toml`
- The recommended lifecycle vocabulary is `validate`, `build`, `create`,
  `describe`, `delete`.
- Packages can support chaining when the workflow engine composes named steps.
- Profile params use kebab-case strings and can be overridden with `BC_PAR_*`.
- Template resources must be packaged and rendered into `.dist/`.
- Safety conventions include no credentials in source and explicit guards for
  destructive operations.

Related site messaging to reuse:

- BigConfig positioning: **The Open Agent Packages Ecosystem**.
- Tagline: **Like Skills, but executable.**
- Packages turn procedural know-how into software agents, humans, shells, CI,
  and scripts can all run.
- Lifecycle verbs let credentials and authority be scoped by action.

## Content positioning

The article should not be a generic “Terraform is bad” post. The stronger and
more defensible claim is:

- Terraform, Helm, Ansible, and Kubernetes operators are powerful tools for
  platform teams.
- The problem is making delivery teams, agents, and CI workflows operate through
  those low-level tool interfaces directly.
- A package can contain those tools but expose a product-like, domain-specific
  operational interface.
- Once a package is a program, the command surface is no longer limited to the
  verbs of the embedded tools.

Use this contrast:

| Old framing | Program/package framing |
|---|---|
| GitOps as configuration files plus a controller/CLI | Packages as executable operational programs |
| `plan`, `apply`, `destroy` as the public interface | Domain verbs: `validate`, `describe`, `backup`, `upgrade`, `rollback`, etc. |
| Humans adapt requirements to Terraform/Helm/Kubernetes APIs | Packages adapt tools to the user’s operational intent |
| Agent must learn every low-level tool | Agent runs a stable package contract |
| Platform tool is the product interface | Platform tool is an implementation detail inside the package |

## Blog article outline

Working title:

> From Terraform Apply to Infrastructure Programs

Suggested structure:

1. **Open with the stuck DevOps loop**
   - DevOps innovation often reads like “another wrapper around Terraform.”
   - The public interface remains `plan`, `apply`, `destroy`, or a pile of YAML
     operated by a CLI/controller.
2. **The old assumption: code was expensive**
   - GitOps and configuration-first tools made sense when writing and
     maintaining custom operational software was too expensive for most teams.
   - Teams adapted requirements to the tool because the alternative was bespoke
     automation nobody could maintain.
3. **The agent-era shift: code is cheap enough to change the abstraction**
   - Agents make it cheaper to create and maintain glue code, tests, adapters,
     and package surfaces.
   - That does not mean unreviewed code is safe; it means we can afford better
     abstractions than low-level CLI wrappers.
4. **A package is now a program**
   - BigConfig packages are normal language packages plus a root `run` file and
     a lifecycle contract.
   - The same package can be run by an agent, a human shell, CI, scripts, or a
     control plane.
   - `bc-pkg` pins GitHub packages or uses local path mode, then forwards
     commands to the package.
5. **The verb surface can match the domain**
   - We are not limited to `plan/apply/destroy`.
   - BigConfig already uses `validate`, `build`, `create`, `describe`, `delete`.
   - Other domains can add `cost-analysis`, `backup`, `restore`, `rollback`,
     `upgrade`, `rotate-keys`, `migrate`, or `audit`.
6. **Kubernetes operators show both the promise and the silo**
   - Operators encode real operational knowledge, but that knowledge is siloed
     inside Kubernetes.
   - Agents often run on a developer machine or in a sandbox; CI runs elsewhere;
     control planes have their own runtime.
   - A package gives all of them a common executable interface without forcing
     everything into the cluster.
7. **Platform teams keep their tools; delivery teams get a package**
   - Platform teams can still use Terraform, Helm, OpenTofu, Ansible, cloud
     SDKs, and operators internally.
   - Delivery teams should not have to learn every low-level provider/tool
     detail to deploy or operate an app safely.
8. **Safety and authority boundaries**
   - `describe` and `validate` can be read-only and agent-friendly.
   - `create` and `delete` can remain human-approved.
   - Packages make those boundaries explicit in code and command surfaces.
9. **Package Spec connection**
   - Point to the BigConfig Package Spec as the minimal external contract:
     one manifest, one root `run`, installable resources, stable lifecycle.
   - Emphasize that the spec gives the minimum vocabulary; a real package can
     expose more verbs when the domain needs them.
   - Mention GitHub SHA pinning and local path development.
10. **Close**
    - Stop forcing delivery teams and agents to operate raw tools.
    - Give them executable packages with the verbs the job actually needs.
    - End with the primary CTA to the homepage (`/`).
