# DevOps Levels of Maturity — A Design Note

## Goal

Document the progression from manual scripts to agent-friendly DevOps operations, and define what makes a workflow safe for agentic execution.

## The Maturity Levels

### Level 01 — Script

A single script that does everything. No configuration separation. The operator edits the script directly to change behaviour. Fragile, opaque, and unrepeatable.

### Level 02 — Script + Configuration File

The script reads a configuration file (JSON, YAML, EDN). The operator edits the config, not the script. The script becomes reusable across environments. This is where most teams operate today.

### Level 03 — Script + Create / Delete

The interface is split into two verbs:

- `create` — provision resources from the configuration.
- `delete` — tear them down.

This is the first step toward an API contract. The script is still imperative, but the entry points are named and predictable.

### Level 04 — Validate + Describe

Two more verbs are added:

- **`validate`** — checks whether the configuration is correct *before* running `create` or `delete`. Deterministic, safe, side-effect-free.
- **`describe`** — reads the current state of the world. Read-only, useful during incidents or drift detection.

This is where agentic DevOps becomes possible.

## Why Level 04 is the Agentic Baseline

An agent cannot safely run `create` or `delete` without supervision — those verbs change state. But `validate` and `describe` are read-only and deterministic. The agent can run them in a loop, unattended, without risk.

The workflow becomes:

1. Agent runs `validate` — is the config syntactically correct? Are tools installed? Are credentials valid?
2. Agent runs `describe` — what does the current state look like?
3. Agent compares the two and recommends the next step to the operator.
4. Operator reviews and runs `create` or `delete` if needed.

This is the core insight: **`validate` is the command the agent can run without risk.** It is the safe primitive that makes the loop autonomous on the read side and gated on the write side.

## What Belongs Inside Validation

Validation is not a single check. It is a bundle of safety gates that must all pass before any state-changing operation:

| Check | What it guards against |
|---|---|
| **Schema validation** | Configuration is syntactically correct (JSON Schema, EDN spec, etc.) |
| **Tooling verification** | Required tools are installed (terraform, kubectl, docker, etc.) |
| **Credential check** | Credentials are present and valid (not expired, not empty) |
| **Domain-specific checks** | e.g. Docker image names exist in the registry, DNS names resolve, ports are available |

If validation passes, the operator can trust that a subsequent `create` is likely to succeed. If it fails, the operator knows exactly what is wrong before executing anything.

## The Agent Boundary

### Anti-pattern: Agents with full credentials

The tempting approach is to give the agent the same credentials as the operator. This is risky because the agent cannot be held accountable for mistakes, and a prompt injection or hallucination could trigger a destructive `delete`.

### Pattern: SSH ForceCommand over MCP

Instead of a broad MCP server that exposes infrastructure operations, use SSH `ForceCommand` CLIs as policy enforcement points:

- The agent calls a narrow, pre-approved CLI over SSH.
- The remote `ForceCommand` enforces exactly what the CLI is allowed to do.
- The agent never has direct access to powerful commands like `terraform apply` or `kubectl delete`.

Why not MCP? For this use case, MCP adds unnecessary abstraction. A constrained SSH command is simpler to audit, easier to reason about, and harder to misconfigure. The agent only needs access to `validate` and `describe` — that surface is small enough to model as explicit CLI calls rather than a full protocol.

## DevOps in One Sentence

> Describe your desired state and run a command to make it happen.

The question is: *which command should the agent run?*

The answer is `validate`. It is deterministic, it is safe, and it gives the agent a productive loop to operate in without handing over the keys to production.

## Summary

| Level | Verbs | Agent-friendly |
|---|---|---|
| 01 | Script | No |
| 02 | Script + Config | No |
| 03 | Create + Delete | Partial (risky) |
| 04 | Validate + Describe | **Yes** |

Level 04 is the target. It separates read-only verbs (safe for agents) from state-changing verbs (reserved for operators). It defines what validation means concretely. And it uses narrow, auditable boundaries (SSH ForceCommand) instead of open-ended protocols.

This is the operating model BigConfig is designed to support.
