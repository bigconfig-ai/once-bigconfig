## Source material reviewed

Primary source:

- `src/pages/package-spec.html`

Key facts from the page:

- Page title: **BigConfig Package Spec**.
- It is a friendly implementation guide for building a repository that `bc-pkg`
  can pin, initialize, and run.
- The launcher contract is intentionally small:
  - one root language manifest: `deps.edn`, `package.json`, or `pyproject.toml`
  - one root `run` file
  - installable package code
  - a command surface that forwards to the BigConfig lifecycle
- Scope note to preserve exactly:
  - there are Python and npm implementations of the launcher
  - there is no Clojure implementation of `bc-pkg` itself
  - both launchers can run Clojure target packages
- The spec covers:
  - quick checklist for package authors
  - package shape by language
  - GitHub SHA pinning
  - local path development mode
  - generated consumer files
  - root `run` file contract
  - lifecycle verbs: `validate`, `build`, `create`, `describe`, `delete`
  - profiles and `BC_PAR_*` params
  - templates/resources packaging
  - safety conventions
  - author test matrix and troubleshooting

Related context to reuse from the site messaging:

- BigConfig positioning: **The Open Agent Packages Ecosystem**.
- Short tagline: **Like Skills, but executable.**
- Packages make procedural knowledge executable, composable, testable, versioned,
  and runnable by agents, humans, CI, shells, and scripts.

## Blog article shape

Working title and slug:

> Announcing the BigConfig Package Spec

Slug/path:

> `announcing-bigconfig-package-spec`

Narrative:

1. Open with the problem: operational knowledge is easy to demo once, but hard
   to package so another human, agent, shell, or CI job can run it reliably.
2. Introduce the Package Spec as the small contract that makes a BigConfig
   package launchable by `bc-pkg`.
3. Explain the minimal repository contract:
   - exactly one supported manifest
   - root `run` file
   - installable code/resources
   - stable command surface
4. Explain why `bc-pkg` pins GitHub refs to commit SHAs and why local path mode
   exists for live development.
5. Explain the lifecycle verbs as authority/safety boundaries:
   - `validate`
   - `build`
   - `create`
   - `describe`
   - `delete`
6. Explain language portability without overstating launcher implementations:
   - packages can be Clojure, Python, or TypeScript targets
   - launchers are Python and npm implementations
   - both launchers can run Clojure targets
7. Explain what authors must package beyond code:
   - templates/resources
   - generated artifacts under `.dist/`
   - params and `BC_PAR_*` overrides
   - safe placeholder defaults in copied `run` files
8. Include runnable examples with both launcher implementations:
   - `uvx bc-pkg owner/repo@ref package validate`
   - `npx bc-pkg owner/repo@ref package validate`
   - local path examples for development mode
9. Explain why this matters for agents:
   - agents need explicit executable contracts, not only prose instructions
   - safe verbs can be run by agents/CI; destructive verbs stay reviewable
10. Close with a CTA:
   - read `/package-spec/`
   - build a package
   - test both GitHub and local path flows with `uvx bc-pkg` and/or `npx bc-pkg`

Possible pull quote:

> The package spec is deliberately small because the point is not to make every
> package look the same inside. The point is to make every package runnable from
> the outside.
