## BigConfig selling points to emphasize

- **Executable package interface:** packages expose verbs such as `validate`,
  `create`, `describe`, `delete`, `build`, `upgrade`, `backup`, `restore`, or
  domain-specific commands instead of forcing users through low-level tool
  commands.
- **Agent-native operations:** an agent can run the same package interface as a
  human or CI job; it does not need to become a mediocre Kubernetes, Terraform,
  Helm, Ansible, and cloud-console operator at once.
- **No mandatory Kubernetes runtime boundary:** BigConfig can operate from a
  local shell, CI, a sandboxed coding agent, a VM, or a separate control plane.
  If a control plane is needed, it can be a normal backend application built on
  the same package logic rather than a Kubernetes-first API server.
- **Composes existing tools instead of replacing them:** Terraform/OpenTofu,
  Ansible, Helm, Kubernetes, cloud APIs, and scripts can remain implementation
  details inside the package. Running only one underlying tool remains trivial
  when needed; package authors can render the right context and delegate to the
  tool directly, e.g. `npx . tofu render tofu:init -- tofu plan`.
- **Package-manager mental model:** pinned package source, package instance
  directories, local-path development, reproducible generated manifests, and
  safe lifecycle verbs.
- **Separation of use from development:** delivery teams operate package
  instances; platform teams develop package source.
- **Imperative lifecycle support where desired-state reconciliation is awkward:**
  migrations, backups, validation reports, staged rollouts, SMTP/DNS handoffs,
  post-provision configuration, and multi-tool workflows can be first-class
  commands.
- **Testability and normal software structure:** package logic can be written,
  composed, reviewed, and tested as software instead of stretching YAML and CRDs
  into an accidental programming model.
- **Higher code reuse across interfaces:** the same package implementation can
  be reused by a CLI, an agent, CI, scripts, a containerized operator workflow,
  and a later backend/control-plane application.
- **Direct agent execution without MCP/API ceremony:** when the package and the
  agent can run on the same computer, BigConfig can skip the extra layer of
  designing an API first and then an MCP adapter only to let the agent call it.
- **Credential separation without a cluster:** containers can provide different
  credential contexts, such as read-only/advisory access for the agent and
  separate mutating credentials for the human/operator fix path.

## Crossplane shortcomings to make central

These are not side notes; they are the buyer-guide case for replacing Crossplane
with BigConfig. The conclusion should be clear throughout: BigConfig replaces
Crossplane by preserving the platform-abstraction goal while moving the
operational boundary to executable packages.

1. **Kubernetes is a runtime dependency.**
   Crossplane needs a Kubernetes control plane before it can be the platform
   control plane. That creates bootstrapping, availability, upgrade, and access
   questions for infrastructure that exists before or outside the cluster.

2. **The abstraction boundary is CRDs and YAML.**
   XRDs, Compositions, patches/transforms, provider configs, claims, and managed
   resources are powerful, but they create a specialized platform language that
   delivery teams and agents must understand or route around.

3. **Reconciliation is not the same as an operational workflow.**
   Desired-state convergence is excellent for many resources, but some jobs are
   naturally procedural: validate, preview, migrate, backup, restore, rotate
   keys, coordinate DNS/SMTP handoffs, generate reports, or run a staged
   multi-tool deployment.

4. **Debugging crosses several layers.**
   Failures can hide behind claims, composite resources, composed managed
   resources, provider controllers, events, conditions, and external cloud API
   state. That is a different debugging experience than running an executable
   package and receiving command-scoped output.

5. **Everything tends to become a Kubernetes resource.**
   That is elegant when Kubernetes is the platform center. It is awkward when the
   caller is a local agent, a CI job, a non-Kubernetes control plane, or a team
   that wants a package CLI rather than another API surface.

6. **Lifecycle verbs beyond create/update/delete are not first-class.**
   Crossplane can model resources and claims, but platform operations often need
   richer domain verbs and reports. Those usually become extra controllers,
   functions, scripts, CI jobs, or external tooling.

7. **Provider and composition operations add their own platform burden.**
   Teams must manage Crossplane providers, credentials, RBAC, CRD versions,
   composition versioning, finalizers, deletion semantics, and cluster-level
   upgrades.

8. **Agent ergonomics are indirect.**
   Agents can edit manifests or call Kubernetes APIs, but the safe public
   contract is not naturally “run this package command and inspect the result.”

9. **The control-plane API is overvalued in the agent era.**
   Crossplane assumes a Kubernetes API boundary first. But with agents, many
   human-in-the-loop operations can run locally: the agent and package run on the
   same computer, with containers providing credential separation. That removes
   the need to create an API first and then an MCP bridge just to let an agent
   call the API.

10. **Server-side automation should be reserved for autonomous loops.**
    Autoscaling and other non-human-in-the-loop automations belong on a server.
    Human-guided diagnosis, validation, remediation, and package operation do
    not need to pay the Kubernetes control-plane tax by default.

## Proposed article outline

1. **Opening: the platform abstraction problem**
   - Everyone agrees delivery teams should not operate raw low-level cloud
     resources.
   - Crossplane and BigConfig both respond to that problem, but choose different
     boundaries.

2. **Why Crossplane is the wrong boundary**
   - It makes Kubernetes the public operations runtime.
   - It turns platform abstractions into CRDs, YAML, providers, claims,
     composites, conditions, events, RBAC, and reconciliation loops.
   - It asks delivery teams and agents to interact with Kubernetes abstractions
     when what they need is a package command surface.

3. **Where the Crossplane boundary hurts**
   - The platform interface becomes Kubernetes-specific.
   - You need a cluster to manage things that may exist outside the cluster.
   - YAML/CRDs become the public contract.
   - Operational workflows do not always map cleanly to desired-state resources.

4. **BigConfig’s different bet**
   - The package is the product boundary.
   - The command surface is the user and agent interface.
   - Terraform/OpenTofu, Ansible, Helm, Kubernetes, cloud APIs, and scripts stay
     inside the package.

5. **Concrete example**
   - A package that provisions DNS, SMTP, object storage, compute, application
     deploy, and post-provision configuration.
   - Crossplane path: model these as XRDs/compositions/providers inside a
     Kubernetes control plane.
   - BigConfig path: expose `package validate create describe delete` and keep
     the multi-stage implementation hidden.

6. **Why this matters more in the agent era**
   - Agents need a small executable contract.
   - A safe command surface limits blast radius better than giving an agent raw
     access to many low-level tools and APIs.
   - The same package can be run by humans, agents, CI, scripts, containers,
     backend apps, and control planes.
   - The package and agent can run on the same computer; do not create an API
     first and an MCP bridge second when local execution is enough.
   - Containers can split credentials so the agent can advise or validate while
     the human/operator uses a separate mutating context for fixes.

7. **Control planes are backend apps, not holy grails**
   - A control plane is just a backend application around operational logic.
   - BigConfig package logic can be reused inside such a backend application
     without making Kubernetes the runtime tax for every operation.
   - Keep server-side automation for autonomous loops such as autoscaling.
   - Keep human-in-the-loop diagnosis, validation, remediation, and package
     operation close to the agent/operator when that is simpler and safer.

8. **How to replace Crossplane with BigConfig**
   - Keep the Crossplane lesson: publish platform abstractions instead of raw
     cloud resources.
   - Replace the Kubernetes API/CRD boundary with a package command boundary.
   - Move provider credentials, multi-step workflows, validation, reports,
     deletion policy, upgrades, and Kubernetes/Helm/Terraform/Ansible details
     inside the package implementation.
   - Even if Kubernetes remains part of the platform, treat it as one tool
     inside the package rather than the universal platform API server.

9. **CTA**
   - Primary CTA: Package Spec (`/package-spec/`).
   - Supporting links: Manual (`/manual`) and homepage/demo if useful.
