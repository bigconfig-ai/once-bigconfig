## Source review notes

### From `from-terraform-apply-to-infrastructure-programs.mdx`

Core thesis:

> DevOps is stuck because low-level tool commands are still the public interface
> to operations. Once the package is a program, the public interface can expose
> domain verbs that agents, shells, CI, and control planes can run.

Important points to reuse:

- Another Terraform wrapper is not a new operating model.
- Terraform, Helm, Ansible, Kubernetes operators, and cloud APIs remain useful inside the package.
- The problem is exposing those low-level tool interfaces directly to delivery teams and agents.
- GitOps/config-first workflows made sense when custom operational software was expensive.
- The agent era makes glue code, adapters, report builders, and package surfaces cheap enough to maintain.
- A package can expose verbs beyond `plan`, `apply`, and `destroy`:
  - `validate`
  - `build`
  - `create`
  - `describe`
  - `delete`
  - `cost-analysis`
  - `backup`
  - `restore`
  - `rollback`
  - `upgrade`
  - `rotate-keys`
  - `audit`
  - `migrate`
- Kubernetes operators prove operational knowledge should be code, but they silo that knowledge inside Kubernetes.
- Agents need an executable contract and a clear boundary between read-only advice and state-changing authority.

### From `skills-vs-bigconfig-packages.mdx`

Core thesis:

> Skills and BigConfig packages are both containers for procedural knowledge.
> Skills make agents smarter. BigConfig makes procedures runnable.

Important points to reuse:

- A skill is agent-native procedural knowledge.
- A BigConfig package is shell-native procedural knowledge implemented as software.
- BigConfig packages can be run by humans, agents, CI, scripts, containers, and other packages.
- BigConfig packages have first-class software properties:
  - dependencies
  - library reuse
  - abstraction
  - composition
  - tests
  - versioning
  - package-level APIs
- The strongest safety model is layered:
  1. skill/instructions teach the agent how to reason;
  2. BigConfig package executes the operational procedure.
- The package provides concrete verbs and durable artifacts; the skill alone is only instructions.

### From `introducing-bigconfig-package.mdx`

Useful historical/context points:

- BigConfig Package was introduced as a response to Helm’s Kubernetes-only center of gravity.
- The early framing emphasizes unified delivery of infrastructure and software.
- The Clojure/Babashka motivation is useful for explaining why package logic should be live, inspectable, scriptable, and library-backed.
- The shell / REPL / library triangle is a strong developer-experience point:
  - shell for command execution;
  - REPL for debugging and experimentation;
  - library for deep automation.
- Walter is a concrete example of infrastructure and workstation/application setup delivered as a package.

Caveats for the new talk:

- Do **not** describe BigConfig packages as only Clojure repositories. The current Package Spec is polyglot: Clojure, Python, and TypeScript target packages.
- Do **not** say there is no launcher. The current system has `bc-pkg` as a bootstrap launcher; the better claim is that there is no monolithic domain-specific CLI required for every package.
- If mentioning Babashka/Clojure, frame it as an origin story or one implementation path, not the current whole product definition.

### From `package-spec.html`

Current contract to explain accurately:

- A BigConfig package is a normal language package with one extra convention: a root `run` file.
- The launcher contract is intentionally small:
  - exactly one root manifest: `deps.edn`, `package.json`, or `pyproject.toml`;
  - one root `run` file;
  - installable package code/resources;
  - a stable command surface.
- `bc-pkg` exists as Python and npm launcher implementations; both can run Clojure target packages.
- GitHub mode resolves refs to 40-character commit SHAs and pins them.
- Local path mode supports live package development.
- Generated consumer files are language-native.
- Recommended lifecycle vocabulary:
  - `package validate`
  - `package build`
  - `package create`
  - `package describe`
  - `package delete`
- Packages can support chained commands when their workflow composes named steps.
- Params use kebab-case strings and support `BC_PAR_*` environment overrides.
- Templates/resources are packaged and rendered into `.dist/`.
- Safety conventions:
  - no credentials in source;
  - destructive actions require explicit guards;
  - validation/describe should be runnable before mutation.

## Proposed talk thesis

A BigConfig package is the missing execution layer between agent instructions and low-level infrastructure tools.

Skills package procedural knowledge for agents. Terraform, Helm, Ansible, and Kubernetes operators encode operational knowledge in specialized runtimes. BigConfig packages turn that knowledge into executable software with a stable command surface that humans, agents, CI, scripts, and control planes can all run.

Short version:

> Skills make agents smarter. BigConfig packages make operations runnable.

Even shorter:

> The package is the program.

## Proposed narrative arc

1. **Problem:** DevOps still exposes low-level tool interfaces as the product interface.
2. **Old cost model:** configuration-first/GitOps made sense when operational software was expensive to write and maintain.
3. **Agent-era shift:** it is now cheap enough to maintain package glue, validation, adapters, report builders, and workflow code.
4. **Skills insight:** procedural knowledge should be packaged and reusable.
5. **BigConfig leap:** procedural knowledge should also be executable, testable, versioned software.
6. **Package contract:** one manifest, one root `run`, installable resources, stable lifecycle verbs.
7. **Agent boundary:** read-only verbs (`validate`, `describe`, `build`) can support agent advice; state-changing verbs (`create`, `delete`, `rollback`, `upgrade`) require explicit authority.
8. **Platform/delivery split:** platform teams keep expert tools inside the package; delivery teams and agents operate the package surface.
9. **Close:** stop exposing assembly language; give agents and teams executable packages.

Suggested slides for the full technical talk (~44 slides):

### Part 1 — The interface problem

1. **Title** — BigConfig Packages: Skills, but Executable
   - Audience cue: a technical talk for Agentic DevOps leaders.
2. **Thesis**
   - Skills make agents smarter. BigConfig packages make operations runnable.
3. **DevOps innovation feels stuck**
   - Another Terraform wrapper, another dashboard for plans, another YAML dialect.
4. **The public interface is too low-level**
   - `terraform apply`, `helm upgrade`, `kubectl apply`, provider schemas, CI conventions.
5. **Tool commands are not product interfaces**
   - Delivery teams ask domain questions; platforms answer with tool verbs.
6. **The old cost model explains how we got here**
   - GitOps/config-first workflows were rational when custom operational software was expensive.
7. **The agent era changes the cost curve**
   - Glue code, report builders, adapters, and package surfaces are cheaper to write and maintain.
8. **But the safety problem gets sharper**
   - Agents should not become mediocre Terraform/Helm/Kubernetes operators.
9. **Required abstraction**
   - A stable executable contract between agent instructions and low-level tools.

### Part 2 — Skills and procedural knowledge

10. **Skills got the key abstraction right**
    - Name the procedure, package it, reuse it.
11. **Operations are procedural knowledge**
    - Provision, render, validate, configure DNS/SMTP, run tools in order, report state.
12. **Concept mapping**
    - Skill ↔ Package; instructions ↔ workflow; context files ↔ resources/templates.
13. **Where skills stop**
    - Agent-native, runtime-bound, limited library reuse, weak artifact contract.
14. **BigConfig package = executable skill**
    - Shell-native, library-backed, testable, versioned software.
15. **Runnable by more than agents**
    - Humans, agents, CI, scripts, containers, and control planes all call the same command surface.
16. **Layered model**
    - Skill/instructions guide reasoning; BigConfig package executes the operational procedure.

### Part 3 — The BigConfig package contract

17. **What is a BigConfig package?**
    - A normal language package plus one root `run` file and a stable lifecycle contract.
18. **Polyglot target shape**
    - Clojure: `deps.edn`; TypeScript: `package.json`; Python: `pyproject.toml`.
19. **The launcher contract is intentionally small**
    - One manifest, one `run`, installable code/resources, command surface.
20. **How `bc-pkg` runs a GitHub package**
    - Resolve ref to 40-char SHA, generate consumer project, copy `run`, forward argv.
21. **How local development mode works**
    - Local path target, native local dependency, symlinked `run`, no SHA pinning.
22. **The `run` file handoff**
    - Safe defaults, editable user config, argv forwarded to package CLI/workflow.
23. **Lifecycle vocabulary**
    - `package validate`, `build`, `create`, `describe`, `delete`.
24. **The package is not limited to five verbs**
    - Domains can add `cost-analysis`, `backup`, `restore`, `rollback`, `upgrade`, `audit`.
25. **Workflow engine model**
    - Opts map threaded through named steps; subworkflow isolation; runner seam for commands.
26. **Profiles and params**
    - Kebab-case params, `BC_PAR_*` overrides, profile composition.
27. **Templates and durable artifacts**
    - Package resources render into `.dist/`; artifacts can be inspected outside the agent conversation.
28. **Testability contract**
    - Pure report builders, injected side effects, fake runners in tests.

### Part 4 — Once as the concrete package example

29. **Once: an infrastructure package, not a Terraform folder**
    - A BigConfig package that composes rendering, Tofu, DNS, SMTP, Ansible-local, and Ansible.
30. **Once command surface**
    - `package validate`, `package build`, `package create`, `package describe`, `package delete`.
31. **Once create pipeline**
    - `tofu` → `tofu-smtp` → `tofu-dns` → `tofu-smtp-post` → `ansible-local` → `ansible`.
32. **Build before mutation**
    - Render artifacts into `.dist/` without applying changes.
33. **Agent-friendly inspection commands**
    - `validate`, `build`, and `describe` support analysis before authority is granted.
34. **Demo: agent-ready prompt**
    - `- run npx bc-pkg bigconfig-ai/once@typescript package validate`
    - `- iterate on failure`
35. **Demo: shell command**
    - `npx bc-pkg bigconfig-ai/once@typescript package build`
36. **Demo: pinned vs local package flow**
    - GitHub ref for consumers; local path mode for package authors.

### Part 5 — Safety, leadership model, and close

37. **Authority boundary**
    - Read-only/no-credential verbs for advice; write verbs require explicit authority.
38. **Credential model by verb**
    - `build`: no credentials; `validate`/`describe`: read-only; `create`/`delete`: read-write.
39. **Kubernetes operators proved the idea, then siloed it**
    - Operational knowledge as code is right; trapping it inside one runtime is the limit.
40. **Platform teams keep the tools**
    - Terraform, Helm, Ansible, operators, and APIs become implementation details.
41. **What Agentic DevOps leaders should standardize**
    - Package contracts, verb safety, artifact locations, test seams, publication/versioning.
42. **Package author checklist**
    - Manifest, `run`, resources, lifecycle verbs, pure reports, no credentials, tested launcher flow.
43. **Adoption path**
    - Wrap one painful workflow; add `validate`/`describe`; publish a pinned package; teach agents the contract.
44. **Close / CTA**
    - Skills make agents smarter. BigConfig packages make operations runnable.
    - Links: homepage, Package Spec, Manual.
