# Blog plan: Agentic DevOps in practice

## Goal

Write a blog article titled **"Agentic DevOps in practice"**.

The article should explain a practical operating model for using agents with BigConfig packages safely: launch a disposable Docker sandbox with `bc-pkg`, run the agent inside the sandbox with read-only credentials, let the agent use `describe` and `validate`, and keep `create` and `delete` as operator actions.

## Main thesis

Agentic DevOps is not about giving an agent the same power as the operator. The safe pattern is to give the agent a constrained environment and a constrained interface:

1. Disposable sandbox.
2. Read-only credentials.
3. `describe` and `validate` for investigation.
4. Agent suggests next steps.
5. Operator performs `create` or `delete`.

## Prominent command

Show this command near the top of the article:

```bash
npx bc-pkg bigconfig-ai/bc-pkg shell
```

Explain that:

- `bc-pkg` is the launcher.
- It launches Babashka `bb` through `npx`.
- Node.js/npm tooling is enough to invoke the launcher.
- No local Babashka installation is required.
- `bigconfig-ai/bc-pkg` is passed to `bc-pkg` as the repository containing a `bb.edn`.
- The `bb.edn` contains a `shell` task.
- The `shell` task uses Docker and the repo's `Dockerfile` to create a disposable container sandbox.
- The agent runs inside that sandbox.

## Correct terminology

- `bigconfig-ai/bc-pkg` is **not** a BigConfig package.
- It is a repository containing:
  - a `bb.edn`
  - a `shell` task
  - a `Dockerfile`
- A BigConfig package is what the agent/operator will operate from the sandbox.

## BigConfig package verbs

A BigConfig package has four verbs:

- `create`
- `delete`
- `validate`
- `describe`

Explain the operational split:

| Verb | Credentials | Default actor | Purpose |
|---|---|---|---|
| `describe` | Read-only | Agent in sandbox | Inspect current state |
| `validate` | Read-only | Agent in sandbox | Check whether reality matches expectations |
| `create` | Full credentials | Operator | Provision or change resources |
| `delete` | Full credentials | Operator | Destroy resources |

Agents can technically run `create` or `delete` if given full credentials, but the article should present that as a conscious risk decision. The golden path is that the operator runs `create` and `delete` themselves.

## Golden path workflow

Use this flow as the core pattern:

```text
operator
  -> launches sandbox with bc-pkg
  -> starts pi.dev agent inside sandbox
  -> provides read-only credentials only
  -> asks agent to run describe/validate
  -> receives recommended next step
  -> operator decides and runs create/delete when needed
```

Key point:

> The agent advises. The operator acts.

## Credentials model

Emphasize:

- The sandbox should only receive read-only credentials.
- The operator's full credentials should stay outside the sandbox.
- `describe` and `validate` are the safe agent-facing interface.
- `create` and `delete` require full credentials and should normally be performed by the operator.

## SSH ForceCommand pattern

Introduce SSH `ForceCommand` CLIs as policy enforcement points.

Explain:

- `describe` and `validate` often need to interact with external systems.
- That interaction should happen through narrow, auditable command boundaries.
- SSH `ForceCommand` is a simple policy enforcement point.
- It enables controlled external-world access without giving the agent broad credentials or broad network/API access.

Suggested phrasing:

> Use SSH ForceCommand CLIs as policy enforcement points. They let the sandboxed agent call narrow, pre-approved commands for `describe` and `validate`, while keeping the real authority outside the sandbox.

## MCP comparison / anti-pattern

Frame MCP carefully:

- ForceCommand is simpler than MCP for this pattern.
- MCP can be overkill when the task only needs a narrow, auditable command boundary.
- Avoid creating MCP servers when a simple SSH ForceCommand CLI is enough.

Anti-pattern:

> Building a broad MCP interface for privileged infrastructure operations when a constrained ForceCommand CLI would be safer and easier to reason about.

## Patterns to promote

- Run agents inside disposable Docker containers.
- Launch the sandbox with `bc-pkg`.
- Use `describe` and `validate` for agent investigation.
- Give the sandbox read-only credentials only.
- Keep `create` and `delete` with the operator.
- Use SSH ForceCommand CLIs as policy enforcement points.
- Follow the BigConfig package verb pattern consistently.

## Anti-patterns to warn against

- Giving the agent full operator credentials by default.
- Letting the agent perform `create` or `delete` without explicit operator awareness.
- Running agents directly on the operator's host environment.
- Building MCP servers where a ForceCommand CLI would be simpler.
- Designing packages without a clear separation between read-only and state-changing operations.
