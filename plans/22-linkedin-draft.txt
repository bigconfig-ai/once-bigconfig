After reading that Bun was rewritten from Zig to Rust, I decided to do the same thing to BigConfig. 🦀

Then I deleted the hand-written version and redeployed with the agent-written one.

That was the real test. 🧪

BigConfig started as a hand-written Clojure stack.

Then I tried an experiment: could an agent port the broader BigConfig stack across languages without losing the contract?

First: TypeScript.
It worked. ✅

Then: Python.
It worked again. ✅

Then came the surprise: I used the TypeScript version as the source to regenerate the Clojure version too. 👀

So now the BigConfig stack — Selmer, BigConfig, Once, and the package/runtime layer around them — exists across TypeScript, Python, and Clojure as agent-written software.

This was not just syntax translation.

Some things had to break. 🔧

Language-specific assumptions had to become generic contracts:

1️⃣ the same workflow shape
2️⃣ the same lifecycle verbs
3️⃣ the same parameter flow
4️⃣ the same rendered artifacts
5️⃣ the same package behavior

That made the system more generic, and cleaner.

Then came production. 🚀

The public BigConfig website, bigconfig.ai, is deployed with `once`: a BigConfig package with validate/build/create/describe/delete workflows and disaster-recovery-oriented deployment behavior.

So I deleted the manually written BigConfig version and deployed the agent-written one.

No incident. ✅

That is the part I care about.

Agents are not only useful for throwaway glue code.

If the system has clear contracts, reusable libraries, tests, review, and durable artifacts, agents can write serious operational software across languages.

BigConfig's thesis is simple:

Procedural knowledge should not only live in prompts or runbooks.

It should be executable, composable, testable, versioned, and runnable from the shell.

Like Skills, but executable. ⚙️
